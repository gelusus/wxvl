风险**来源：**  
所有服务Web请求的PHP安装，包括PHP-FPM、Apache带mod_php、php-cgi、FrankenPHP和LiteSpeed。我们认为mod_php的风险最高，已有验证漏洞利用，未经认证的请求可以在任何应用代码运行前触发攻击。  
  
**漏洞：**  
- **通过OOM损坏**  
处理RCE，CVE-2026-109618：内存不足处理可能会中断PHP，而内部请求数据仅部分初始化。请求清理时可能会将无效数据视为有效。  
  
- **通过陈旧全局状态**  
获取RCE，CVE-2026-109619：请求拥有内部状态在其备份存储器被释放后仍可存续。同一工作者处理的后续请求可能会在正常初始化重置前使用该过时状态。  
  
**更新方式：**  
- 更新至 PHP 8.5.12、8.4.27、8.3.36 或 8.2.35。原始码下载可在我们的下载页面。Windows源代码和二进制文件是同一页的。  
  
- Linux发行版和LTS厂商会提前收到补丁，所以请查看你的供应商是否有更新的包。  
  
- **PHP 8.1及更早**  
版本不再接收PHP项目的更新。一些发行版和LTS厂商提供回溯修复，详情请联系你的供应商，或升级到支持的版本。  
  
- 如果您依赖志愿者维护的系统，我们建议您切换到分发包或从源头构建，以便立即应用更新。仓库今天不会有更新。rpms.remirepo.net  
- 鉴于这些漏洞的严重性，PHP 安全团队为 PHP 7.4、PHP 8.0 和 PHP 8.1 提供了极少的源码回溯移植，帮助源代码构建者或无法访问 LTS 厂商的用户。  
  
**如果无法立即更新：**  
虽然只有更新才是完整的解决方案，但以下措施可以减少特定攻击路径的风险，但并不能保证安装安全。

针对 CVE-2026-109618，官方建议在暂时无法升级时，以管理员配置强制设置 memory_limit=-1  
，并确认池、目录或应用配置不会重新设置有限的 PHP 内存上限。修改后需要重启所有 PHP 工作进程。  
  
这一建议看起来与通常的资源保护原则相反，但有明确原因：它移除了攻击者可以利用的、可控的 PHP 请求内存限制失败点。它**不会阻止底层内存分配失败**  
，也不是完整修复。  
  
同时，解除 PHP 自身的请求内存限制会带来资源耗尽风险，因此必须配合请求限制和外部资源边界。官方建议包括：  
- • 不需要文件上传的应用，将 post_max_size  
 设为 8M  
；需要上传时，公告给出的建议值为 32M  
，并保持 upload_max_filesize  
 小于 post_max_size  
。  
  
- • 在 Web 服务器或代理层限制解码后的请求体大小、输入字段数量、multipart 分段数量、头部数量和嵌套深度；这些限制也应覆盖没有可用 Content-Length  
 的请求。  
  
- • 不使用 multipart 表单的应用，可以在前端阻止这类请求进入 PHP。  
  
- • 使用容器或 cgroup 提供可用性边界，并尽可能让资源超限只终止受影响的工作进程；如果限制作用于整个容器或进程组，也可能一起终止主进程和其他工作进程。  
  
**不要用 RLIMIT_AS 或 RLIMIT_DATA 替代上述措施。**  
 技术公告指出，它们可能直接造成底层内存分配失败，重新触及存在漏洞的处理路径。容器或 cgroup 限制也不保证彻底避免分配失败，仍不能替代补丁。

部署时可以先检查命令行环境：  
```
php -v

```  
  
但这两条命令只说明 CLI 的版本和配置，不能证明 FPM、Apache 模块或容器中的 PHP 已经更新。多版本共存、不同服务使用不同镜像或独立安装目录时，尤其需要分别核对。  
  
实际升级至少应完成以下步骤：  
1. 1. 盘点对外处理请求的 PHP 服务、版本、软件包来源和镜像，而不只检查开发机或 CLI。  
  
1. 2. 安装上述修复版本，或确认发行版、LTS 厂商的软件包已经包含对应 CVE 的补丁。  
  
1. 3. 重建并部署使用旧 PHP 的容器镜像，重启或完整滚动替换工作进程，确保没有旧实例继续接收请求。  
  
1. 4. 在实际 Web 运行环境确认版本和配置，检查关键业务路径及错误日志；不要把公开暴露 phpinfo()  
 页面作为长期验证方式。
