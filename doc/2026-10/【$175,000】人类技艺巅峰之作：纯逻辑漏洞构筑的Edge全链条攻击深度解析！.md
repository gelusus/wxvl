## 攻击探索之旅：从浏览器导航机制开始

(navigation)机制"开始深入研究吧。在本文中，我不会陷入过多技术细节的泥潭，毕竟在这个时代，你完全可以随时请教你的AI助手来补全技术细节:)

## 被遗忘的角落：导航节流器的安全隐患  
  
在深入分析Chromium的导航流程时，一个名为"**导航节流器(Navigation Throttles)**  
"的组件引起了我的高度关注。这些节流器**驻留在浏览器进程中**  
，负责拦截所有由浏览器或渲染器发起的导航请求。也许我现在说这话有点事后诸葛亮，但从过去五年谷歌Chrome修复的**3000多个CVE漏洞**  
来看，与导航节流器相关的却**不足20个**  
。足见这确实是一个**被安全研究人员长期忽视的技术角落**  
。  
  
于是我开始了对导航节流器的深度挖掘，重点分析了谷歌Chrome和微软Edge的不同实现。在代码审计过程中，我意外发现Edge为支持其企业级**Entra ID**  
(微软统一身份认证平台)功能，专门实现了一个名为EdgeCAGuidanceNavigationThrottle**的特殊节流器(其中的CA代表Conditional Access条件访问)。这个节流器的核心功能是：当Edge检测到用户在微软网站使用工作账户登录时，智能引导用户切换到正确的用户配置文件。要触发这个节流器，必须从特定的**  
微软自有域名源(如login.live.com  
)发起导航：  
```
// 触发条件访问引导的特定URL格式location.href = \`https://guidance-ca-error/?email={目标邮箱}&switch_profile={跳转URL}\`
```  
  
一旦节流器被触发，Edge会**对比当前用户配置文件的邮箱**  
与URL参数中的?email={目标邮箱}  
字段。如果不匹配，Edge会弹出对话框引导用户切换账户。  
  
  
![](https://mmbiz.qpic.cn/sz_mmbiz_png/TKdPSwEibsZiaNzqow8kYfDTA8YBlKG1DxNkkgXOaUw2SZeJhKaU0SH6DYLh5bVjhyzBiaickJIuic1VBZewlibIcicULsiboPueIb9huedFdgK1teM/640?wx_fmt=png&from=appmsg "")  
  
但如果邮箱完全匹配，Edge就会从switch_profile={跳转URL}  
参数中提取用户原本的目标URL，然后通过Chromium的**内部导航API**  
发起一个新导航：  
```
NavigateParams params(browser, switch_profile_url, ui::PAGE_TRANSITION_LINK);params.disposition = WindowOpenDisposition::CURRENT_TAB;  // 关键设置：在当前标签页打开params.window_action = NavigateParams::SHOW_WINDOW;Navigate(&params);  // 执行浏览器进程级别的导航
```  
  
**简单来说**  
：当目标URL符合特定的内部格式时，节流器会取消原始导航，然后在条件满足时使用攻击者控制的查询参数中的URL**创建一个由浏览器进程发起的新导航**  
。由于这个新导航具有**浏览器进程的权限级别**  
，理论上我们可以实现一些通常无法做到的操作：例如跳转到通常被禁止访问的**浏览器内部页面**  
(如edge://settings  
、devtools://...  
)甚至是**JavaScript伪协议页面**  
(如javascript:alert(origin)  
)。  
  
不过，虽然JavaScript伪协议看似强大，但要触发节流器首先需要**在login.live.com上获得执行上下文**  
。所以，即使能够跳转到javascript:  
伪协议，实际上**并没有提供额外的能力**  
——充其量只是个**自XSS(Self-XSS)攻击，或者说是将开放重定向转化为XSS的一种方式。无论如何，攻击者的JavaScript执行都局限在login.live.com的同一上下文中**  
。  
  
说实话，我一开始并没有太重视这个漏洞。在我眼中，它充其量只是个**强化版的开放重定向**  
，虽然能够跳转到更多浏览器级协议页面，但**仍然需要与其他漏洞配合**  
才能构成实际威胁。所以这个漏洞在我的笔记里静静躺了好几个星期……🤦♂️  
## 意外的突破：无源导航带来的UXSS全新攻击面  
  
真正的转折点出现在某一天我重新审视Chromium架构时的一个关键闪念：**节流器是在浏览器进程中处理的，所以新导航也是由浏览器发起的。然而，触发节流器的页面login.live.com却运行在渲染器进程中，而且我在代码研究中没有找到任何将浏览器与特定渲染器绑定在一起的逻辑。那么……代码中的CURRENT_TAB究竟指的是哪个标签页呢？**  
  
为了验证这一猜想，我设计了一个巧妙的测试：给原始触发条件添加**人工延迟**  
：  
```
setTimeout(function(){    location.href = \`https://guidance-ca-error/?email={目标邮箱}&switch_profile={跳转URL}\`}, 8000)  // 8秒延迟给用户切换标签页的时间
```  
  
在延迟期间，我们手动将Edge**切换到另一个完全不同的标签页**  
(比如google.com  
)，然后观察会发生什么……  
  
![](https://mmbiz.qpic.cn/sz_mmbiz_png/TKdPSwEibsZjFVDrtbqC0uBQ5EyV80d0HMCmscu1Mnjl9e6SyYJROSu0Jd61Jjatlequz951sUibJlqjjALIOVEEmRnvXfIRAodIMvuHHsRFQ/640?wx_fmt=png&from=appmsg "")  
  
太棒了！我们在**google.com上实现了UXSS！**  
 这就是整个攻击链的第一个核心漏洞。为了深入理解UXSS的根本原因，我们仔细分析了Chromium的源代码，发现了一个关键逻辑：如果调用Navigate()  
时没有明确指定source_contents  
参数(即要绑定的渲染器源)，Chromium会自动将**当前活动标签页**  
作为导航的渲染器源。  
  
↓ **详细的代码执行路径:**  
```
base::WeakPtr<content::NavigationHandle> Navigate(NavigateParams* params) {// [...]// [关键代码段1] 如果没有指定源WebContents，我们使用目标浏览器的选中项// 这必须在GetBrowserAndTabForDisposition()有机会替换|params->browser|之前发生if (!params->source_contents && params->browser) {    params->source_contents = params->browser                  ->GetBrowserForMigrationOnly()                  ->tab_strip_model()                  ->GetActiveWebContents(); // <--- [1] 使用当前活动标签页作为导航源  }// [...]// [关键代码段2] 如果没有指定目标WebContentsif (!contents_to_navigate_or_insert) {    DCHECK(!params->url.is_empty());    if (params->disposition != WindowOpenDisposition::CURRENT_TAB) {      // [...]    } else {      // ...在当前标签页加载的情况下，目标与源相同      DCHECK(params->source_contents);      contents_to_navigate_or_insert = params->source_contents;   // <--- [2] 设置为目标WebContents    }    // [关键代码段3] 执行实际导航    if (!HandleNonNavigationAboutURL(            params->url, contents_to_navigate_or_insert->GetBrowserContext())) {      NavigationController::LoadURLParams load_url_params =          LoadURLParamsFromNavigateParams(contents_to_navigate_or_insert,                                          params);      navigation_handle =          contents_to_navigate_or_insert->GetController().LoadURLWithParams(              load_url_params);     // <--- [3] 启动导航；向Mojo下游分发    }// [...]}
```  
  
虽然这条代码路径要求params.disposition  
为CURRENT_TAB  
且params.source_contents  
为NULL  
，但**幸运的是，这两个条件正好是代码的默认设置**  
！就连Chromium自身的实现都陷入了这个陷阱。在我看来，这绝对应该被视为**一个全新的UXSS攻击面**  
！  
## 攻防博弈：零点击攻击的四大技术挑战  
  
我们刚刚发现的UXSS原语听起来确实强大，但在实际攻击场景中，要成功触发它仍然面临**四大技术挑战**  
。下面我们将逐一剖析这些挑战，并讲解如何通过串联更多漏洞来突破它们😉。  
### 挑战一：节流器必须从受信任的源触发  
  
正如我之前提到的第一个挑战：UXSS必须从特定的**微软自有域名页面**  
触发。理论上我们可以尝试在这些网站上寻找XSS漏洞来实现，但这显然是费时费力的苦差事，只能作为最后的选择。我们决定首先检查**源验证机制**  
中是否存在一些容易利用的"低垂果实"。  
```
content::WebContents* web_contents = navigation_handle()->GetWebContents();const GURL last_committed_url = web_contents->GetLastCommittedURL();if ( !IsSupportedLoginUrl(last_committed_url) )    return content::NavigationThrottle::CANCEL_AND_IGNORE;
```  
  
我们发现EdgeCAGuidanceNavigationThrottle  
使用GetLastCommittedURL()  
来**获取触发导航的来源页面**  
并进行检查。乍一看这似乎是标准的验证方式，但仔细想想就会发现问题：微软似乎完全忘记了**导航请求不仅可以来自当前网页窗口，还可以来自其他窗口**  
！因此，一个简单的**跨窗口window.open(...)操作**  
就足以完全绕过这个验证：  
  
↓ 你可以在任意网站执行以下代码来触发节流器  
```
popup = window.open('https://login.live.com/', '_blank')popup.location = \`https://guidance-ca-error/?email={目标邮箱}&switch_profile={跳转URL}\`
```

 默认会阻止window.open(...)  
这类操作。

### 挑战三：目标浏览器未登录用户配置文件的问题  
  
现在我们可以从任何地方触发EdgeCAGuidanceNavigationThrottle  
了，但还需要通过**条件访问(CA)的严格检查**  
。代码逻辑首先要求**微软Edge必须有已登录的用户配置文件**  
，然后才会验证?email={目标邮箱}  
是否与配置文件中的电子邮件匹配。只有两个条件同时满足，我们才能进入无源浏览器的导航流程，最终触发UXSS。  
```
Profile* current_profile = Profile::FromBrowserContext(    web_contents->GetBrowserContext());std::string email;net::GetValueForKeyInQuery(target_url, kEmailQueryKey, &email);const base::FilePath target_profile_path = GetPathOfProfileWithEmail(email);if (current_profile->GetPath() != target_profile_path) {    profiles::SwitchToProfile(target_profile_path, false, BindOnce(…));}
```  
  
我们不能假设攻击环境一定存在已登录的用户配置文件，所以需要找到一种方法**即使在未登录状态下也能让攻击生效**  
。在探索微软Edge生态系统时，我们发现了一个极为便利的特性："**OneAuth**  
"。这个功能允许任何Edge WebView应用程序在访问微软网站时**自动使用当前MSA(微软账户)凭据登录**  
。更重要的是，从**Windows 11 25H2版本**  
开始，系统初始设置过程(OOBE)强制要求用户**使用MSA账户登录**  
(除非采用本地账户的变通方案)。这意味着，即使用户从未在浏览器中创建过用户配置文件，仅仅访问www.microsoft.com  
网站就足以让Edge自动创建配置文件并完成登录！

## 组件完美整合：零点击攻击链的最终成型  
  
到目前为止，为使核心攻击原语顺利工作，我们已经成功串联了**四大关键技术组件**  
：  
1. **源头绕过漏洞**  
：源于缺失**跨窗口Opener检查**  
  
1. **弹窗拦截绕过**  
：源于微软Edge内部的**硬编码白名单**  
  
1. **自动认证机制**  
：微软的**OneAuth特性**  
自动完成用户登录  
  
1. **信息泄露途径**  
：源于**CORS配置错误**  
导致的邮箱信息泄露  
  
**现在我们终于可以实现无需用户任何点击的UXSS攻击了！**  
 更棒的是，由于UXSS是由**浏览器进程**  
直接发起的(如果深入研究，你会发现这是在Mojo通信层的HandleRendererDebugURL  
处触发的)，它可以**完全无视任何CSP(内容安全策略)的限制**  
。这意味着我们可以在google.com  
、facebook.com  
、icloud.com  
或任何其他网站上任意执行JavaScript代码！  
## 挣脱束缚：从浏览器沙箱到系统级权限  
  
我们确实获得了强大的通用XSS能力，但这真的意味着我们可以为所欲为吗？在**Web安全**  
的范畴内，答案当然是肯定的。但我们的终极目标是**实现任意代码执行(ACE)**  
，仅有UXSS还远远不够。我们需要找到**突破浏览器沙箱**  
的方法，将JavaScript执行能力转化为真实的系统级代码执行。  
  
我脑海中浮现的第一个也是最直接的想法是：既然我们可以在任意网站(更准确地说，任何源)执行JavaScript，为什么不直接**利用特权WebUI页面**  
如edge://settings  
或edge://downloads  
来获取代码执行呢？  
  
然而，这种"天真"的想法早已被Chromium开发者们预见并防御了。在**渲染器进程的Mojo处理层**  
，有一个额外的安全检查：如果JavaScript来源属于以下**特权WebUI页面**  
，渲染器会直接忽略JavaScript URL请求。  
```
edgechrome-extensionchromechrome-untrustedchrome-distillerchrome-errorchrome-nativechrome-searchdevtools// 更多...
```  
  
*↓ **具体的代码路径分析:**  
*  
```
void LocalFrame::LoadJavaScriptURL(const KURL& url) {  // 保护特权页面免受书签工具和其他JavaScript操纵的影响  if (SchemeRegistry::ShouldTreatURLSchemeAsNotAllowingJavascriptURLs(          GetSecurityContext()              ->GetSecurityOrigin()              ->GetOriginOrPrecursorOriginIfOpaque()              ->Protocol())) {    return;  // <--- 如果属于黑名单中的协议，直接返回，不执行JavaScript  }  // [...]}
```  
  
*↓ **协议检查的实现细节:**  
*  
```
bool SchemeRegistry::ShouldTreatURLSchemeAsNotAllowingJavascriptURLs(    const String& scheme) {  DCHECK_EQ(scheme, scheme.LowerASCII());  if (scheme.empty())    return false;  return GetURLSchemesRegistry().not_allowing_javascript_urls_schemes.Contains(      scheme);  // <--- 检查协议是否在黑名单中}
```  
  
**简单来说**  
：Chromium团队几乎将所有你能想到的**特权WebUI协议都列入了not_allowing_javascript_urls_schemes黑名单**  
。在这个阶段，我的研究确实陷入了长时间的瓶颈期。😖  
## 巧妙突破：通过沉浸式阅读器实现任意文件写入  
  
然而，在我们继续深入挖掘微软Edge特性的过程中，我们注意到Edge有一个名为Immersive Reader**的阅读模式组件。与Chrome内置的阅读模式不同，Edge的沉浸式阅读器似乎是**  
从Chromium早期版本分叉而来，并由微软在其基础上进行了大量定制开发。因此，Edge没有采用Chrome的chrome-distiller://  
协议或被黑名单禁止的chrome-untrusted://  
协议，而是使用了**自定义的read://协议**  
。而微软似乎**忘记将这个自定义协议添加到JavaScript限制黑名单中**  
了，这意味着我们的UXSS在**这个特权WebUI页面上可以正常工作！**  
:)  
  
从这个特权WebUI页面出发，我们可以通过JavaScript访问**大量原生的C++对象**  
。其中一个特别引起我注意的API是chrome.edgeFeedbackPrivate.zipDiagnosticLogFiles()**。经过测试验证，这个函数接受两个参数：一个**  
文件名**和一个**  
JSON字符串：  
  
↓ 我们在read://https_orange.tw/?url=https://orange.tw页面上测试了这个功能  
```
chrome.edgeFeedbackPrivate.zipDiagnosticLogFiles(    'LOL.ZIP',  // 用户指定的ZIP文件名    '{        "logFiles": {            "ORANGE": "AAAAAAAA"  // 要写入的文件内容和文件名        },        "deviceInfo": {1337: 1337}    }'  // JSON格式的日志数据)
```  
  
在深入研究和测试过程中，我们观察到微软Edge会**首先创建一个临时文件夹**  
，将内容AAAAAAAA  
写入文件ORANGE.json  
，然后将整个文件夹打包成LOL.ZIP  
文件，上传到微软服务器，最后清理所有临时文件。当然，我们会立即尝试**目录穿越路径注入**  
……是的，该API确实**允许../路径跳转**  
逃逸临时文件夹。但让人烦恼的是.json  
扩展名总是被自动添加。你可能也在想：用**空字节(NULL Byte)**  
 能去除扩展名吗？**当然可以！**  
  
现在我们拥有了一个**任意文件写入原语**  
，可以**同时控制文件名和文件内容**  
，并能够**覆盖任意路径下的任意文件**  
！

## 协议的终极掌控：通过覆盖protocols.json实现自动化协议处理器启动  
  
至此，我们几乎已经集齐了所有必要的攻击组件。最后一步挑战是：如何将**浏览器级别的任意文件写入**  
转化为**任意代码执行**  
以完成整个攻击链条。我们观察到微软Edge在初始化过程中会进行一些**有趣的非标准组件加载活动**  
，比如从可写文件夹读取大量配置文件或加载第三方DLL库。  
  
**动态链接库(DLL)的侧加载**  
(DLL side-loading)听起来确实很诱人。然而，由于我们的文件写入数据被**包装在JSON格式**  
中，所有内容必须是**有效的UTF-8字符串**  
。加上微软Edge是一个**64位进程**  
，我们必须投放一个**64位DLL文件**  
。经过一段时间的深入研究，我们发现**无法在UTF-8编码约束下构造出有效的64位PE头**  
，因此不得不放弃DLL侧加载的方案。  
  
我们最终采取了一个**不那么明显但同样有效的替代方案**  
。在深入研究过程中，我们发现除了OneAuth功能外，Edge在初始化时还会加载一系列组件，其中之一就是"**AutoLaunchProtocolsComponent**  
(自动启动协议组件)"。这个组件会从我们可写的文件夹中读取一个名为protocols.json  
的配置文件，该文件定义了**哪些源有权启动哪些URL协议处理器**  
。通过覆盖这个文件，我们就能从**任何源启动任何协议处理器**  
。  
  
↓ 配置文件的标准路径:AppData\Local\Microsoft\Edge\User Data\AutoLaunchProtocolsComponent\1.0.0.10\protocols.json  
```
{  "allow": [    {      "origins": ["https://.get.microsoft.com", "https://.apps.microsoft.com"],      "protocol": "ms-windows-store"// 允许这些源启动Windows应用商店协议    },    {      "origins": [        "https://.onedrive.com",        "https://.onedrive.live.com",        "https://sharepoint.com"      ],      "protocol": "ms-word"// 允许这些源启动Word协议    }    // [...] 更多协议定义  ],"warn": [    // [...] 需要警告的协议配置  ],"block": [    // [...] 被阻止的协议配置  ]}
```  
  
那么如何让微软Edge重新加载我们的修改后的配置文件呢？很简单！利用我们之前获得的**浏览器发起导航能力**  
，直接跳转到edge://restart  
重启页面！:)  
## 从telnet协议到最终代码执行！  
  
为了实现最终的代码执行，我们选择了telnet://  
协议**作为突破口。在Windows系统中，telnet协议处理器会尝试调用**telnet.exe  
可执行文件，但这个二进制文件**默认并未随Windows系统预装**  
。因此，Windows会在**PATH环境变量**  
列出的各个目录中搜索这个文件。而在这些目录中，恰好有一个是**当前用户拥有写入权限的**  
……  
```
C:\WINDOWS\system32C:\WINDOWSC:\WINDOWS\System32\WbemC:\WINDOWS\System32\WindowsPowerShell\v1.0C:\WINDOWS\System32\OpenSSHC:\Users\lowpriv\AppData\Local\Microsoft\WindowsApps    # <--- 这个目录对`lowpriv`用户是可写的！
```  
  
**完美的攻击链至此完成**  
：我们只需要放置一个**精心修改的protocols.json配置文件**  
和一个**32位的微型可执行文件**  
，就能轻松实现任意代码执行。整个漏洞利用的**代码量不到100行**  
，简洁而优雅！  
  
在实际攻击场景中，**浏览器重启步骤并非必需**  
，这个额外的重启操作只是为了满足Pwn2Own竞赛的演示要求。现在就让我们欣赏一下完整的攻击演示视频吧！ 🔥
