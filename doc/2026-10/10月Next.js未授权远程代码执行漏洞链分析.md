## 摘要  
  
2026-10-14，Vercel以带外方式发布Next.js 16.4.1（Active LTS）与15.5.28（Maintenance LTS），修复三枚上游依赖引发的漏洞：两枚Critical级可致未授权远程代码执行（RCE），一枚High级为Server Actions拒绝服务[1]。  
  
本次更新的三个特殊之处：两枚修复原定9月发布，因上游依赖交付延迟而推迟[1]；三枚公告中有两枚**没有CVE编号**  
，且截至本文撰写时尚未进入OSV/npm advisory数据源，主流依赖扫描器存在结构性漏报[2][4]；两枚RCE的根因分别落在React Server Components序列化通道（react-server-dom-*  
）与原生SVG渲染栈（librsvg/libxml2经sharp引入）两个完全不同的层次，却共用同一App Router攻击面。

## 2 漏洞详情  
### 2.1 漏洞一：use cache返回多个typed array的未授权RCE  
  
官方表述（逐字）[2]：  
> "A vulnerability in applications using App router with Cache Component can lead to remote code execution. The application needs to have a use cache  
 function that returns multiple typed arrays."  
> "There is no known workaround for affected applications with such use cache  
 functions. You should upgrade immediately even if your application does not have similar functions."  
  
  
根因在React而非Next.js。上游公告限定条件为："Crafted payloads targeting frameworks supporting React Server Components can lead to remote code execution. This only affects extremely rare cases where responses transport multiple typed arrays and an attacker-controlled value."[5]受影响的是三个RSC序列化绑定包react-server-dom-webpack  
/-parcel  
/-turbopack  
，区间19.0.0–19.0.8、19.1.0–19.1.9、19.2.0–19.2.8、19.3.0。  
  
攻击链三个必要前提，缺一即不成立：  
1. 使用**App Router**  
并启用**Cache Components**  
；  
  
1. 存在返回**多个**  
typed array（Uint8Array  
/ArrayBuffer  
等）的use cache  
函数，典型如返回字节与签名二元组、protobuf/msgpack序列化载荷；  
  
1. 这些数组中包含**攻击者可控值**  
（请求体、query、header、上传字节、外部API响应）。  
  
满足前提时，恶意输入进入RSC（"Flight"）协议的反序列化流程。typed array在Flight载荷中以分块引用表达，**多个**  
typed array的偏移与引用解析存在缺陷路径，可被引导至异常对象并影响后续调用目标绑定，最终在服务端进程上下文执行代码。需明确：**Vercel与React均未公布该缺陷的调用链级细节**  
，本文不对未公开的gadget链作臆测。  
  
历史坐标：这与2025-12的React2Shell（CVE-2025-55182 / CVE-2025-66478，RSC Flight协议原型链污染，CVSS 10.0）落在同一组react-server-dom-*  
包上，但本次范围窄得多——React自己用"extremely rare cases"作了限定[5]。此外Vercel在2026-05的变更日志中已承认，RSC类攻击载荷"表现为正常的HTTP请求结构，WAF层无法可靠拦截"，该结论对本次同样适用。  
### 2.2 漏洞二：Image Optimization处理SVG的未授权RCE（CVE-2026-96889 / VectorFreed）  
  
官方表述（逐字）[3]：  
> "A memory-related vulnerability has been discovered in an upstream library used for Image Optimization can lead to possible remote code execution (RCE) when Next.js runs on glibc-based Linux."  
> "Ensure the version of sharp  
 used by Next.js is greater than or equal to 0.35.5  
."  
  
  
这不是Next.js的代码缺陷，而是原生栈内存破坏的穿透——公告给出的缓解与修复动作都落在sharp版本上，而非Next.js自身的优化器代码。数据路径：  
```
攻击者 → GET /_next/image?url=<attacker-hosted>&w=...&q=...
      → Next.js Image Optimization
      → sharp → libvips (VipsForeignLoadSvg) → librsvg + libxml2   ← CVE-2026-96889
      → 原生进程内存破坏 → glibc Linux上可稳定化为代码执行

```  
  
发现者@rafabd1（Rafael B. Dias）将该链命名为VectorFreed，机制如下[7]：SVG可通过xi:include  
引入另一个SVG文档；脆弱路径中，**libxml2在外层文档展开实体时，librsvg已开始解析被包含文档**  
；若被包含SVG声明**同名实体**  
，librsvg会替换并**释放**  
第一个实体对象，而libxml2仍持有其指针；被包含文档解析结束后，libxml2继续用这一**悬垂指针**  
写入，此时该内存可能已归属其他对象。结果是崩溃，而"**in other cases this also led to command execution**  
"。这是两个解析器对同一文档树并发持有可变状态导致的生命周期不一致（owner-confusion UAF），不是简单越界写。

### 2.3 漏洞三：App Router Server Actions拒绝服务  
  
官方表述（逐字）[4]：  
> "Crafted requests targeting Next.js applications using App Router with at least one Server Action can lead to excessive CPU usage blocking processing of further requests in the same process."  
> "Applications using Pages Router or not using Server Actions are not vulnerable."  
  
  
上游React公告表述更宽："...this could lead to out-of-memory exceptions or excessive CPU usage."[5]两点不一致：React侧同时提到**OOM与CPU耗尽**  
，Next.js侧只强调CPU；且React公告正文段落把受影响版本写作19.0.0–19.0.7/19.1.0–19.1.8/19.2.0–19.2.7，而页面表格列出19.0.0–19.0.8/19.1.0–19.1.9/19.2.0–19.2.8/19.3.0，**同一公告内部自相矛盾**  
——做资产判断时按更宽的表格取保守值[5]。  
  
利用门槛极低：只需应用中存在至少一个Server Action，无需其被业务调用、无需认证。Next.js默认以有限进程数处理请求，CPU打满后同进程全部请求排队，等效全站不可用。除升级外无workaround。

### 3.3 漏洞二复现要点  
  
VectorFreed仓库提供的是面向多条输入路径的**SVG生成器**  
，定位是"验证use-after-free"，而非通用RCE武器[7]。本文只描述形态。  
```

<svg xmlns="http://www.w3.org/2000/svg"     xmlns:xi="http://www.w3.org/2001/XInclude" width="64" height="64">
  <!DOCTYPE svg [ <!ENTITY shared "..."> ]>   <!-- 外层：libxml2 在此展开实体 -->
  <rect width="64" height="64"/>
  <xi:include href="inner.svg" parse="xml"/>  <!-- 内层：声明同名实体，触发 UAF -->
</svg>

```

**四条必须知道的验证边界：**  
- rafabd1明确声明：**"这个链没有通用RCE PoC，载荷需按目标逐一定制"**，且**  
"目前公开的大部分所谓PoC并未复现真实RCE链"**，其中一些靠SVG的<foreignObject>  
制造"执行"效果——那不是本漏洞的利用路径[7]。看到这类PoC跑出效果应判断为误报。  
  
- 该README早期版本称尚无完整SVG→命令执行的公开利用，更新版则提到完整可用利用已公开，同时提醒"以当前工具从已公开的bug与patch反推完整链是可行的"[7]。**"尚无在野武器化"不构成拖延修复的理由。**  
  
- 加固良好的Node官方构建（PIE+RELRO）上多数只观察到崩溃；非PIE构建上ROP链稳定性显著提高。**"我们容器里只是500报错"不代表不可利用**，只代表当前构建形态下未稳定化。  
  
- 只升级系统librsvg无效：sharp预构建走@img/sharp-libvips-*  
捆绑副本[7]。  
  
### 3.4 漏洞一与漏洞三的验证要点  
  
漏洞一因官方未公开细节且无公开PoC，**目前没有可靠的远程判定手段**  
，可执行验证限于：版本面（16.0.0≤next≤16.4.0且react-server-dom-*  
在受影响区间）、能力面（Cache Components已启用）、构造面（3.2静态审计命中并人工确认可控值进入缓存返回值）。若前两者成立，即使构造面无命中仍应升级——官方"即使没有类似函数也立即升级"的措辞本身说明作者无法穷举触发形态[2]。  
  
漏洞三的验证限于行为面：确认应用存在'use server'  
指令，然后在靶标内观察单进程CPU能否被拉满并阻塞后续请求。载荷形态是RSC action请求体（Next-Action  
 header+multipart/form-data  
），**在网络侧与正常请求无异**  
，无法靠"请求是否畸形"拦截[4][5]；可检测的是同一来源短时间高频命中action端点+单进程CPU阶梯式上升。

### 4.4 检测信号  
- **工具盲区（必须正视）**  
：漏洞一与漏洞三无CVE编号，三枚10-14公告截至检索时尚未进入OSV / GitHub Advisory全局库 / npm advisory feed，npm audit  
与多数SCA会结构性漏报[2][4]。**处置依据应是lockfile版本比对+代码审计，而非SCA绿灯。**  
  
- **网络侧**  
：对/_next/image  
与图像/OG路由监控URL参数中的编码SVG特征（%3Csvg  
、<!DOCTYPE  
、ENTITY  
、xi:include  
、foreignObject  
）；对Server Action端点监控异常频率与请求体大小分布。**不要指望WAF拦截RSC载荷**  
——其结构合法。  
  
- **主机/EDR侧**  
：Node.js进程派生shell或子进程（sh  
/bash  
/python  
/curl  
）、异常出站连接、.next/  
之外落盘的可执行文件、worker异常退出与OOM、CPU/内存基线偏离、Image Optimization错误率突升。  
  
- **在野利用**

### 4.5 关于Vercel托管  
  
Vercel平台是否自动完成sharp与librsvg升级、本次三枚公告对托管应用的影响，**官方博客与安全公告均未明确说明**  
，本文不作推断。已明确的是：8月批次官方表示Vercel托管不受影响[6]。**自托管（ECS/VPS/K8s/Docker/裸机）必须自行升级**  
，这也是本次公告的主要受众。  
## 5 结论  
  
Next.js 16.4.1 / 15.5.28处理的是三条彼此独立但攻击面重叠的缺陷：use cache  
返回多个typed array触发的RSC反序列化RCE（16.x专属、无CVE、无workaround）、经sharp→libvips→librsvg的SVG use-after-free RCE（横跨10.0.0–16.4.0、glibc Linux、依赖版本核验是关键）、Server Actions CPU耗尽DoS。三者共同点是**未认证可达**  
、**WAF无法可靠拦截**  
、**修复动作在依赖层而非应用代码层**  
。  
  
这轮漏洞也暴露了两点结构性问题。其一，Next.js把librsvg、libxml2、libheif、libvips等内存不安全的C/C++代码放进了Web请求同步路径，并由未认证GET驱动——同一缺陷在桌面场景是CVSS 7.8的本地问题，在框架里就成了CVSS 9.5的网络问题[3][8]；任何"图像优化"这类服务端能力都应按RCE组件做威胁建模。其二，框架方对上游CVE的处理方式是"版本bump+公告"，交付节奏受上游支配，"官方已修复"与实际依赖到位之间存在真实时滞，因此验收标准必须是依赖树实际解析结果而非"我们升到最新了"。  
  
处置优先级：自托管且启用Cache Components的16.x应用、任何启用dangerouslyAllowSVG  
或使用Node运行时next/og  
的10.x–16.x应用按P0；其余13.x–16.x按P1（DoS面）；15.5.x用户升级后**必须复验sharp版本**  
。所有在补丁窗口期内暴露的应用，应把密钥轮换与失陷排查纳入处置流程，而非止步于版本升级。
