### 1、背景介绍  
  
污点分析（taint analysis）是漏洞检测里最常用的技术之一，思路并不复杂：把不可信的外部输入标记为 source，把危险操作（比如 strcpy  
 的目的缓冲区、system  
 的命令参数）标记为 sink，然后追踪数据能不能从 source 流到 sink，能流到就报一个潜在漏洞。  
  
但这个思路有个前提：你得先告诉分析工具哪些函数是 source、哪些是 sink。这套人为定义的规则叫"污点规范"（taint specification）。规范的质量直接决定检测效果——漏标一个 source，整条污点流就凭空消失；错标一个 sink，产出的告警就是误报。传统做法几乎全靠人工维护规范，Java 生态里 FlowDroid 等工具积累了相对完整的列表，但人工标注覆盖不全、语义歧义（同一个函数在不同参数位置上角色可能完全不同）的问题始终存在。  
  
IRIS（arXiv:2405.17238）针对这个痛点提出：让 LLM 自动推断污点规范，再把规范交给 CodeQL 做全仓库漏洞检测。论文用真实数据支持了这个主张——在自建的 120 个真实漏洞数据集 CWE-Bench-Java 上，CodeQL 基线只检出 27 个，IRIS 结合 GPT-4 检出 55 个，还发现了 4 个现有工具都找不到的未知漏洞。  
  
我对这个方法中LLM标注source和sink的可行性进行了探究。我使用的是c++代码和deepseek模型。  
### 2、探究问题与验证设计  
  
要验证"可行性"，不能只复述论文结果，得把它拆成可以独立回答的子问题。我定义了三个 RQ：  
- **RQ1（知识可行性）**  
：LLM 对 API 污点语义的"知识"到底靠不靠谱？能不能准确判断一个函数是 source、sink、污点传播器还是无关函数？  
  
- **RQ2（工程可行性）**  
：这些标注接进污点分析引擎后，能不能支撑真实的端到端漏洞检测？  
  
- **RQ3（边界在哪里）**  
：哪些场景会失败？失败是模型能力问题还是方法设计问题？  
  
验证载体是我写的一个小型管线 iris-cpp：用 CodeQL 的 FunctionCall  
/getTarget()  
 谓词提取"有调用点但无函数定义"的外部 API 作为候选（对应 IRIS 论文 3.2 节的候选提取思想），批量交给 DeepSeek 按固定 JSON schema 打标（函数全限定名、类型、sink 参数下标、污点输出位置），再把 JSON 标签自动转换成 CodeQL 谓词、接入标准污点追踪查询。管线本身只是工具，五个阶段的实现细节不展开。  
  
评估设计成两层，分别对应 RQ1 和 RQ2：**测试集 A**  
 做函数级标注质量评测（29 个函数，其中特意混入 10 个冷门的 C 标准库和 Windows API，与人工逐字段比对）；**测试集 B**  
 做端到端评测（10 个手写用例，覆盖 CWE-120、CWE-78 的正报与负报、净化函数、跨函数传播、多 sink 等场景）。两套用例严格不相交，避免"拿例题考模型"。  
### 3、可行性分析  
  
**RQ1：知识可行性——成立，且有意外之喜。**  
 测试集 A 上，LLM 的类型判定准确率 100%，字段级完全匹配率 96.6%。更值得注意的是修正过程：我对着语义定义逐条核对时发现，几个冷门 API 上 LLM 的标注比人工初版答案更全面准确——LLM 相当于"读过"海量真实代码里这些 API 的用法，而人凭记忆标注反而容易想当然。这印证了 IRIS 论文的核心假设：LLM 确实内化了相当一部分污点语义知识，而且这种知识不依赖特定语言生态。  
  
**RQ2：工程可行性——基本成立。**  
 测试集 B 的 10 个用例通过了 9 个，包括：CWE-120 缓冲区溢出和 CWE-78 命令注入的正报、负报（不该报的不报）、净化函数场景、fgets  
 这类"污点通过输出参数带出"的 source、返回值型 source、跨函数过程间传播、多 sink 多告警。也就是说，自动生成的标注接进引擎后，端到端行为与人工标注的预期基本一致。  
  
**RQ3：边界清晰，且失败模式可归因。**  
 唯一失败的用例和测试集 A 唯一的标注错误是同一类根因。除此之外还有两个工程层面的适配点：一是 C++ 大量输入函数的污点通过指针参数带出而非返回值（如 fgets(buf, size, stream)  
），schema 里必须单独设计 tainted_output  
 字段，否则这类 source 全部漏标——这是方法移植的语言适配成本，不是模型能力缺陷；二是 LLM 偶发返回空标签，用重试逻辑即可兜底。  
  
**跨设置对照**  
。把我的小规模结果和论文原文放在一起看：原文是 Java + GPT-4 + 120 个真实漏洞的大规模验证，我是 C++ + DeepSeek + 29 函数/10 用例的小规模验证，两者模型不同、语言不同、规模不同，但结论方向一致——LLM 标注污点规范都达到了"可用水准"。这基本排除了"结论绑定特定模型/语言"的担忧，是对可行性的一个有力佐证。  
### 4、Case Study：变参函数的下标偏移  
  
唯一贯穿两套测试的失败模式来自变参函数。测试集 B 的 t09 用例是 scanf  
 到 strcpy  
 的污点流：scanf  
 从标准输入读入字符串，流入 strcpy  
 的目的缓冲区，应报缓冲区类告警。但模型在标注 scanf  
 时把污点位置标到了格式串参数 p0，而不是真正接收输入的缓冲区参数 p1，端到端告警随之丢失。测试集 A 里 fscanf  
 的同类错误也是这个根因。  
  
原因不难理解：变参函数的参数个数在编译期不确定，模型按固定签名"数格子"时容易错位。这属于 RQ3 识别出的模型能力边界，而非方法不可行。  
### 5、结论  
  
回到开头的问题：LLM 自动标注污点规范可行吗？我的答案是：**可行，但带边界条件**  
。在 29 个函数上 100% 的类型判定准确率和测试集 B 9/10 的端到端通过率，足以支撑"可用水准"的判断；边界在于变参函数的参数计数、以及跨语言移植时 schema 的适配成本。IRIS 原文用大规模真实数据集给出了产业级的肯定答案，这次小规模独立验证至少说明：这个方向不是大厂大模型的专利，一个学生用便宜的模型、另一种语言，也能复现出方向一致的结果。
