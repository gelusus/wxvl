PHP 是互联网的“隐形地基”：主流电商平台、市场平台（marketplace）、学习管理系统（LMS）的底层架构由 PHP 编写；WordPress、Drupal、Joomla 等内容管理系统（CMS）同样运行在 PHP 之上——而它们  
   
支撑着互联网上的大多数网站  
   
。  
  
也正因如此，PHP 核心中一个“无需认证即可执行代码”的漏洞，从来不只是某一家公司的问题，而是  
   
整个互联网需要共同面对的风险  
   
。本文编译自卡巴斯基官方博客发布的安全通告，为你梳理漏洞详情与企业防护建议。

01  
OVERVIEW  
### 什么是 PHP2Shell：两个未授权远程代码执行漏洞  
  
  
PHP 开发团队近日发布补丁，修复两个严重漏洞：攻击者可借此  
   
在无需认证的情况下  
   
，于运行 PHP 的服务器上  
   
远程执行任意代码  
   
。两个漏洞的编号分别为  
   
CVE-2026-109618  
   
与  
   
CVE-2026-109619  
   
，针对它们的利用工具被命名为  
 **PHP2Shell**  
   
。  
  
开发团队已为所有受支持的分支发布更新。但值得注意的是，在补丁正式发布之前，  
   
针对这两个漏洞的利用尝试就已经出现  
   
——换句话说，攻击者的起跑线，比很多运维团队的打补丁计划更早。  
  
  
02  
AFFECTED VERSIONS  
### 受影响的 PHP 版本  
  
  
据 PHP 官方网站信息，  
   
8.2.35、8.3.36、8.4.27 与 8.5.12 之前的版本  
   
，均受这两个漏洞影响。只要你的版本低于对应分支的上述数字，就  
   
在受影响之列  
   
。  
  
更早的分支已无官方修复。据非官方报告，漏洞的  
   
影响范围可追溯至 5.4.0  
   
起的各个版本——这个数字意味着，大量仍在生产环境运行的旧系统，可能都暴露在攻击面上。  
  
💡 请立刻对照版本：若系统运行的是 8.1 或更早版本，官方升级通道已关闭，需走厂商 backport 或分支迁移路线（详见第 04 节）。  
  
  
03  
RISK ANALYSIS  
### 漏洞为何危险：从内存残留到远程代码执行  
  
  
两个漏洞在 CVSS v4.0 评分体系中均获得  
   
9.2 分  
   
（满分 10 分），属于“严重”级别。其根因是：当一个请求被中断时（例如因内存不足），PHP 会  
   
在内存缓冲区中留下无效数据  
   
，并在随后对其发起访问——攻击者可以借此在服务器上执行代码。  
  
9.2  
  
CVSS v4.0 评分（两个漏洞同分）  
  
2  
  
个未认证远程代码执行漏洞  
  
5.4.0  
  
据非官方报告的最早受影响版本  
  
已经确认的一条攻击链，利用了 PHP 默认开启的  
   
session.upload_progress  
   
机制——该机制原本用于跟踪文件上传进度。由于它默认启用，  
   
攻击者无需任何额外条件  
   
即可触达漏洞入口。  
  
成功利用之后，攻击者能够以  
   
Web 服务器进程的权限  
   
远程执行代码，且  
   
全程无需认证  
   
。据 PHP 开发团队说明，所有处理 Web 请求且未打补丁的安装都有风险，覆盖 PHP-FPM、Apache mod_php、php-cgi、FrankenPHP 与 LiteSpeed 等主流部署方式。  
  
其中  
   
风险最大的是 mod_php  
   
。研究人员演示的利用链中，一个未认证请求  
   
甚至在应用代码开始执行之前  
   
就能触发攻击——应用层的一切  
   
防护逻辑都来不及介入  
   
。  
  
「未打补丁的 PHP，等于把 Web 服务器进程的权限，交给一个陌生的 HTTP 请求。」  
  
  
04  
MITIGATION  
### 企业防护：四条核心建议  
  
  
以下建议由 PHP 开发团队与卡巴斯基专家共同整理，按优先级排列。  
  
1  
立即升级 PHP：优先升级可从互联网访问的系统，升级至  
 **8.5.12、8.4.27、8.3.36 或 8.2.35**  
   
。源代码可在 PHP 官网获取；若使用发行版软件包或主机商提供的 PHP，请检查是否有更新包——Linux 发行版与 LTS 厂商已提前收到补丁；服务器由主机商托管的话，直接要求其完成升级。  
  
2  
8.1 及更早版本：另寻出路。这些版本已不在 PHP 项目的更新范围内，请向发行版厂商或 LTS 支持提供商确认是否有 backported（向后移植）修复，  
   
或直接迁移到受支持的分支  
   
。针对 PHP 7.4、8.0 与 8.1，开发团队准备了最小化的源代码 backport，可手动编译，同样发布于 PHP 官网。  
  
3  
重启并验证。升级后重启 PHP-FPM 或 Web 服务器，确保进程加载新代码，并用  
   
php -v  
   
验证版本。若 PHP 来自发行版软件包，记得查看软件包变更日志——补丁后的  
   
版本号可能保持不变  
   
。  
  
4  
排查日志，监测异常。重点检查  
   
10 月 20 日以来的日志  
   
，危险信号是 Web 服务器进程  
   
执行了不该执行的操作  
   
（如启动命令 shell、curl、wget 等）。卡巴斯基解决方案可帮助及时发现恶意活动：针对 Linux 与 Windows 上的 RCE 利用尝试，可用 Kaspersky NEXT EDR Expert 检测；针对网络流量中的 PHP2Shell 利用行为，可用带 NDR 模块的 Kaspersky Anti Targeted Attack（KATA）平台检测。  
  
  
05  
WORKAROUNDS  
### 无法立即更新时的临时之选  
  
  
唯一能彻底解决问题的方式，是  
   
立即安装补丁  
   
。如果暂时无法升级，PHP 开发团队建议先实施  
   
临时缓解措施  
   
，并为每个漏洞提供了详细的分步操作说明（见 PHP 官网 2026 年归档页）。  
  
需要强调的是：缓解措施只是为升级争取时间的权宜之计，  
   
不能替代补丁本身  
   
。在补丁落地之前，请密切监控 Web 服务器进程的可疑行为。  
  
  
∞  
THE END  
### 结语  
  
  
PHP2Shell 的危险之处，在于三个条件的叠加：  
   
未认证即可触达  
   
、默认开启的攻击入口、以及  
   
补丁发布前就已出现的利用尝试  
   
。对仍在运行未修复版本的企业来说，升级窗口期的每一分钟都很关键。  
  
互联网上的大多数网站由 PHP 驱动——补丁每延迟一天，风险敞口就扩大一分。
