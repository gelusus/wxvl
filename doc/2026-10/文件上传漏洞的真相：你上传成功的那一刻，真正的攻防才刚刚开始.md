#  文件上传漏洞的真相：你上传成功的那一刻，真正的攻防才刚刚开始  
原创 www.klsec.com
                    www.klsec.com  昆仑AI安全实验室   2026-10-30 17:05  
  
2026年4月，OWASP核心规则集（CRS）披露了一个叫CVE-2026-33691的漏洞。攻击者只需要在文件名里加一个空格，比如把shell.php  
写成shell. php  
，就能绕过CRS的文件扩展名检查。Metasploit社区很快有人提交了对应的绕过模块  
。  
  
但一位叫Chocapikk的安全研究员在审查这个模块时，发现了一个被所有人忽略的问题。他在PR评论里写道：**WAF绕过是真实的，但文件落盘时扩展名里带着那个字面空格，Apache和IIS都不会把. php映射到PHP处理器。文件只是躺在那里，完全惰性。要让这个绕过真正导致执行，后端应用必须在保存文件之前把空格从文件名里剥掉。他审查的几个目标，没有一个这么做**  
。  
  
这个细节比漏洞本身更有教学价值。它精确地指出了文件上传漏洞在2026年的真正战场：**不在于“能不能传上去”，在于“传上去之后，在谁的解析逻辑里，它变成了什么”。**  
  
WAF说“这是安全的”，后端说“这是一个PHP文件”，浏览器说“这是一个HTML页面”——三个系统对同一个文件做出三种不同的判断，攻击链就活在这三种判断的缝隙里。  
  
**一、WAF层的绕过：CRS的空白填充与Coraza的字符集盲区**  
  
文件上传的第一道关口通常是WAF。2026年的WAF绕过已经很少是“改个扩展名”那么简单，更多是**利用WAF解析逻辑与后端解析逻辑之间的差异**  
。  
  
**CVE-2026-33691的本质是“校验顺序错误”**  
 。CRS在处理上传文件名时，先检查扩展名，然后才对文件名做规范化处理（去除空白字符等）。攻击者提交shell. php  
，CRS检查到的扩展名是. php  
——在它的规则库里，这个字符串不匹配.php  
的黑名单，因为中间有一个空格。CRS放行。但后端如果使用类似trim()  
、strip()  
的方法对文件名做清理，空格被剥掉，shell. php  
变成了shell.php  
，PHP引擎正常解析执行  
。  
  
这个漏洞在Linux和Windows上的可利用性不同。**Windows后端更容易中招**  
，因为Windows的文件名规范化行为（去除尾随空格、点号）比Linux更激进。Linux则需要后端代码显式调用了trim()  
类函数才成立  
。CRS在v3.3.9和v4.25.x LTS中修复了这个问题，修复方式是**调整校验顺序，先规范化再检查扩展名**  
。  
  
**Coraza WAF的CVE-2026-114101走的是另一条路：字符集编码盲区**  
。Coraza在解析Content-Disposition  
头时，使用Go语言的mime.ParseMediaType  
函数。这个函数会**忽略非UTF-8的RFC 5987 filename*参数**  
。攻击者可以提交一个“诱饵文件名”使用标准编码（比如filename="safe.jpg"  
），同时用filename*=iso-8859-1''shell.php  
携带真正的恶意文件名。Coraza基于FILES  
的规则看到的是safe.jpg  
，放行。后端如果按RFC 5987的规范处理filename*  
，拿到的就是shell.php  
。  
  
修复方式是升级到Coraza 3.8.1，并在后端增加独立于WAF的文件验证层  
。  
  
这两个CVE的共同逻辑是：**WAF的“安全判断”建立在一个它自己认为正确的解析结果上，但后端使用的是另一个解析结果。**  
 你不需要攻破WAF，你只需要让WAF看到的东西和后端看到的东西不一样。  
  
**二、MIME与扩展名校验的绕过：参数走私与“信任错位”**  
  
绕过WAF之后，第二道关口是应用层的MIME和扩展名校验。2026年的绕过手法已经从“改扩展名”进化到了**利用HTTP头解析的参数走私**  
。  
  
**CVE-2026-44974（@hapi/content）**  
 是一个教科书级的参数走私案例。这个Node.js库在解析Content-Disposition  
头时，Content.disposition()  
保留重复参数的**最后一个**  
值，而Content.type()  
保留重复charset/boundary参数的**第一个**  
值  
。  
  
攻击者提交：  
```
Content-Disposition: form-data; name="file"; filename="safe.txt"; filename="shell.php"
```  
  
@hapi/content  
的disposition()  
看到的是shell.php  
（最后一个）。但链路上的另一个组件（比如WAF或另一个解析器）如果保留的是第一个值，它看到的是safe.txt  
。**同一个请求，两个组件对文件名的理解完全不同**  
。白名单校验使用safe.txt  
，实际保存使用shell.php  
，绕过成立  
。  
  
**Parse Server的CVE-2026-32728**  
 则是利用了MIME参数的附加语法。Parse Server的扩展名黑名单匹配逻辑在处理Content-Type  
时，没有剥离MIME参数。攻击者提交Content-Type: image/jpeg;charset=utf-8  
，扩展名校验逻辑将整个字符串（包含;charset=utf-8  
）与黑名单比对，匹配失败，放行。但文件本身是一个.php  
或.svg  
，被存储并以应用域名提供服务  
。修复方式是**在验证扩展名之前，先从Content-Type头中剥离所有MIME参数**  
。  
  
**金蝶EAS的uploadlogo接口**  
 是一个真实的企业级应用案例。漏洞的根因很朴素：**过度依赖客户端传来的Content-Type头**  
。攻击者上传一个.jsp  
文件，但把Content-Type  
设为image/jpeg  
。后端只检查了这个头，没有检查文件内容（魔数签名），也没有做后缀白名单校验。JSP Webshell被保存到Web目录并正常执行。这个案例的修复方案覆盖了开发、运维和应急三个层面：开发侧做白名单+内容校验+UUID重命名，运维侧上WAF+目录监控+最小权限，应急侧隔离取证+后门排查。  
  
**三、从上传到RCE：链式利用与运行时层面的“上传后漏洞”**  
  
当应用层的校验被绕过，文件被写到服务器上之后，下一步是让它执行。2026年的趋势是**把上传作为一条更长攻击链的起点**  
，而不是终点。  
  
**Telerik RadAsyncUpload的链式利用**  
 展示了上传组件如何被组合成未授权RCE。TantoSec研究员Marcio Almeida串联了四个漏洞：核心是一个**填充预言机（Padding Oracle，CVE-2026-13182）**  
 。RadAsyncUpload使用AES-CBC加密客户端状态，但没有完整性校验。攻击者通过观察服务器对篡改数据的响应差异（有效填充 vs JSON解析失败），可以解密并**伪造**  
加密的上传配置，而不需要知道密钥  
。  
  
伪造配置之后，攻击者可以指定任意.NET  
类型，控件在没有白名单的情况下解析该类型（CVE-2026-13181），反序列化一个gadget，加载攻击者控制的DLL。上传的DLL是一个混合模式程序集，加载即执行原生代码  
。  
  
这个利用链有明确的前提条件：页面必须渲染了RadAsyncUpload控件、服务器端处理器读取上传结果、且应用配置了**非默认的加密密钥**  
（讽刺的是，Telerik推荐这个设置作为加固措施）。满足条件的站点，利用链的端到端跑完大约需要**127,000次预言机请求**  
，在实验环境中约一小时  
。Progress在2026年7月修复了这条链，没有在野利用的确认报告  
。  
  
**PHP2Shell（CVE-2026-109618/109619）**  
 则把战场拉到了**PHP运行时本身**  
。漏洞出在session.upload_progress  
——PHP的multipart解析器在处理上传进度时，会在模块RINIT运行**之前**  
触发回调。如果在这个时刻发生OOM（内存耗尽），PS(id)  
这个会话ID指针会变成悬空指针，留在worker进程里。下一个请求可以通过伪造zend_string  
头，在这个地址上写入数据，实现堆泄漏和代码泄漏。最终从泄漏的指针构造一个伪造的HashTable  
，将pDestructor  
设置为zif_system  
，达成RCE。  
  
整个利用链是**20个HTTP请求**  
的纯Python脚本，不需要任何扩展，针对nginx → php -S  
的部署环境。这个漏洞的严重性在于：**你不需要上传一个可执行文件**  
。恶意文件只是一个普通的multipart上传请求，利用的是PHP解析这个请求时的内存管理缺陷。任何开启了session.upload_progress  
的PHP 8.2–8.4环境，都在攻击面上。修复版本在2026年10月21日发布。  
  
**四、防守方视角：为什么“在上传点做校验”永远不够**  
  
把这四个层面的案例放在一起看，一个结论非常清晰：**文件上传漏洞的根因，几乎从来不是“上传点没做校验”，而是“上传点的校验假设，在后续的解析、存储、执行环节中不成立”。**  
  
CRS假设“扩展名字符串匹配黑名单就够了”，但后端会trim()  
。@hapi/content  
假设“重复参数只有一个生效”，但链路上的另一个组件可能相反。Parse Server假设“Content-Type  
的值就是MIME类型”，但参数可以附加在后面。金蝶EAS假设“Content-Type  
是image/jpeg  
，文件就是图片”，但文件内容可以是任意东西。RadAsyncUpload假设“加密状态不可伪造”，但没有完整性校验的加密可以被填充预言机攻破。PHP假设“上传进度回调在安全时机执行”，但内存耗尽可能让它在一个指针已经失效之后才触发。  
  
**防御必须沿着“解析链”逐段部署，而不是只在上传点堆校验规则。**  
  
第一层，WAF侧：升级CRS到v3.3.9/v4.25.x以上，升级Coraza到3.8.1以上。但更重要的是，**不要依赖WAF作为唯一防线**  
。Coraza的修复建议里明确写了：在后端应用服务器上实现独立的文件验证逻辑，作为WAF检查之外的**第二道防线**  
。  
  
第二层，应用层：**白名单，而不是黑名单**  
。Parse Server的修复公告里有一句被很多人忽略的话：fileUpload.fileExtensions  
的定位应该是**允许列表**  
，而不是拒绝列表。默认黑名单只覆盖常见危险扩展名，不是穷举，“开发者不应依赖默认值”  
。白名单意味着“只允许.jpg  
、.png  
、.pdf  
”，而不是“禁止.php  
、.jsp  
、.phtml  
”。黑名单永远会漏，白名单不会。  
  
**内容校验**  
同样必要。金蝶EAS的案例说明，只检查Content-Type  
和扩展名是不够的。魔数签名（文件头字节）必须被验证。一个.jpg  
文件的前几个字节不是FF D8 FF  
，它就不是JPEG，无论它的扩展名和MIME是什么。  
  
第三层，存储与执行：**上传目录不可执行**  
。这是最古老也是最可靠的防线。无论攻击者传上来什么，如果Web服务器被配置为不在上传目录中执行任何脚本，文件就只是一个文件。UUID重命名、非Web目录存储、最小权限运行，这些措施的组合效果远大于任何单一规则。  
  
第四层，运行时：**及时修补解释器和框架**  
。PHP2Shell的教训是，文件上传的攻击面延伸到了语言运行时本身。PHP 8.4.27/8.5.12的补丁不是可选项。session.upload_progress  
如果业务不需要，关闭它；需要的话，确保运行在修复版本上。  
  
**写在最后**  
  
文件上传漏洞在2026年仍然高频，不是因为它“简单”，而是因为**它的攻击面分布在解析链的每一层，而每一层的开发者都倾向于假设“上一层已经处理好了”**  
。  
  
WAF假设后端会校验，后端假设WAF会拦截，应用假设框架会处理，框架假设运行时是安全的。攻击者做的事情只有一件：找到那个**所有人都以为别人会管、实际上没有人管**  
的缝隙。  
  
CVE-2026-33691的shell. php  
是一个空格。CVE-2026-44974是一个重复的filename  
参数。CVE-2026-32728是一个;charset=utf-8  
后缀。Telerik的链是一个填充预言机的响应差异。PHP2Shell是一个OOM之后的悬空指针。**每一个绕过都精确地落在两个系统“理解不一致”的那个点上。**  
  
测试文件上传时，不要只问“能不能传.php  
”。问自己：WAF看到的是什么，应用看到的是什么，文件系统保存的是什么，执行引擎解析的是什么。**如果这四个答案不完全一致，你就找到了那条缝。**
