#  Optimizely 供应链投毒：178 家机构官网被挂马，BBC、CNN、Zoom、Salesforce、汇丰、Equifax、宜家在列  
 数说安全   2026-11-18 02:33  
  
![图片](https://mmbiz.qpic.cn/sz_mmbiz_png/kBl5kX6f2oNXdGsgUuc2rgZFHnJMLsJkcNSYz1Zp60jQEKFaZgpbLzod7ySNjfYKLap38d6HTicr2Tmic5YeYECw/640?wx_fmt=other&wxfrom=5&wx_lazy=1&wx_co=1&tp=webp#imgIndex=0 "")  
  
11月16日，一起冲着网站实验平台 Optimizely 去的供应链攻击，让一批知名机构的网站变成了恶意代码的分发入口。  
  
安全公司 Report URI 做了调查，他们拿到并检查了1,611个不同的Optimizely脚本，结果发现其中188个被污染了，牵连到名单里的178家组织——BBC、CNN、Zoom、Salesforce、汇丰、Equifax 和宜家这些品牌都在里面。  
  
Optimizely随后也确认了这件事：确实有未经授权的攻击者钻了Experimentation产品的漏洞，往部分客户的项目里塞了恶意JavaScript。公司说漏洞已经修好、注入的代码也清掉了，还采取了一些措施保护相关账户。官方事件公告发在11月17日 01:02 UTC，也就是北京时间当天早上09:02。到本文核查的时候，事件页面还挂在"监测中"的状态。  
  
这事儿最关键的一点在于：攻击者是借着客户本来就信任的第三方服务，把恶意代码直接送进了访问者的浏览器。也就是说，企业自己的服务器哪怕一点事都没有，访问者正常逛着页面，照样可能碰到攻击代码。  
  
Optimizely是干什么的？简单说就是给网站做A/B测试和个性化推荐的。比如企业想给不同的访问者展示不同的文案、按钮或者页面布局，然后比比看哪种设计效果更好——要实现这些，网站通常就得加载Optimizely提供的那段JavaScript。  
  
这次攻击走的正是这条现成的分发路径。研究方发现，恶意代码被写进了客户项目的Project JavaScript，也就是projectJS配置里，然后跟着正常脚本一起从cdn.optimizely.com发出去。有些变体还会再多走一步，去加载攻击者自己控制的 1688360[.]cc/track.js。  
  
浏览器那边连的确实是合法CDN，用的也是正常服务的证书，看起来一点问题没有。但加密连接只能保证传输路上不被动手脚，它没法证明供应商返回给你的代码是干净的。真正需要核查的，是代码本身的内容，以及谁能有权发布它。  
  
第三方脚本进了页面之后，也不会因为“我是外部供应商来的”就自动被关进一个独立又安全的沙箱里。按普通脚本方式加载的代码，能在页面权限范围内读内容、改内容、调接口。OWASP 在讲第三方JavaScript风险时，已经把页面变更失控、恶意代码执行和敏感信息泄露列成了主要风险。  
  
至于攻击者最初是怎么进去的，Optimizely向BleepingComputer解释说是Experimentation的账户注册流程里有问题。厂商还说，有问题的路径已经封了、相关活动会话被踢下线、令牌撤销了、受影响账户的访问权限也重置了。不过呢，公开说明里始终没讲代码层面到底是怎么漏洞触发的，所以现在还说不准这具体算哪一种权限绕过，或者是不是跨客户访问的问题。  
  
Report URI记录的最早Optimizely注入观察发生在11月16日04:21 UTC。到当天 21:52 UTC，其发现的 88个受污染脚本中，仅剩一个仍包含恶意代码。研究方随后更新称，截至23:11 UTC，所监测的受污染脚本已全部清理。（这些时间反映研究方的观察结果，不能直接视为攻击的准确起止时间。）  
  
攻击代码的用途也不止一样。早期分析发现，它既能替换加密货币收款地址，也能窃取支付卡信息：前者会悄悄把页面上的、或者你复制时用到的钱包地址换成攻击者的地址，等你随后付款时，钱就打到别人账上了；后者则盯着能碰到的表单提交和网络请求，找卡号、有效期、安全码这类信息。  
  
Hudson Rock对恢复出来的样本又做了进一步分析，还发现了一段有条件触发的Cookie收集和页面图像收集逻辑。这里说的"截图"是对网页内容做渲染，不是操作系统那种屏幕截图。已经分析出来的代码没法直接读取标了HttpOnly的Cookie，也没有证据表明它突破了跨域托管支付框架的隔离。  
  
移动设备也在这条攻击链的关注范围里。研究方把相关的投递路径和Coruna、DarkSword这些iOS利用工具包联系到了一起，后面还披露了更深层的代码阶段。但到目前为止，公开证据还没证明真有受害者的iPhone被成功攻陷，也不能因此就说攻击用了零day漏洞。  
  
研究方列出的组织里包含集团的地区业务，宜家受影响的是家居设计子域client.home-design.ikea.com，非集团官网；  
  
Zoom 已经在官方安全页面上表态：作为预防措施，生产环境里的Optimizely 已经关掉了，目前还没发现客户数据受影响。至于实际暴露了多少人、成功偷走了多少数据、终端感染有多少，这些还得等后续调查。

对网络安全产业来说，这起事件提出了一个要求：  
供应链安全得把运行时交付的代码也纳入进来。  
  
企业可能确实已经把代码仓库、开源依赖、构建流程都检查过一遍了，但页面最终跑起来的那些代码，还可能被营销、分析、客服或者实验平台在网站上线之后不停地更新。只盯着构建环节做检查，是没法自动解释这些后续变化的。  
  
也就是说，除了软件成分分析和软件物料清单，还得再把运行时脚本的管理能力建起来：网站到底实际加载了哪些代码，谁有权改它们，哪些页面依赖这些服务，真出事的时候由谁去停用。供应链安全的资产清单里，得把这些能改变生产页面行为的服务算进去。  
  
组织分工也得跟着调整。现在的常见情况是：营销团队管采购和日常配置，开发团队管把脚本嵌进去，安全团队管事故响应。如果这三方之间没有共同的变更记录和明确的责任人，那外部平台就可能变成一条绕过常规代码审查的发布通道。这次事件确实让浏览器端安全和营销技术安全的需求更受重视了，但还不足以据此推算某类产品能带来多少市场增量。  
  
站在安全产品的角度，重点是两件事：  
你能看见攻击链的哪一段，以及你能约束什么行为。  
  
从部署路径看，主要负责守网站入口的 Web 应用防火墙，未必正好卡在“访问者浏览器直接向第三方CDN拉脚本”这条链路上。终端检测与响应产品也许能发现异常联网或者后续利用动作，但发生在页面内部的地址替换、表单读取，不一定会产生新进程、持久化之类的主机告警。这是防护位置和检测对象本身的差异，不能光凭一份受影响品牌名单，就断定某类产品失效了。  
  
网络侧的控制还是有价值的。Netskope在自己客户环境的遥测数据显示，对攻击相关域名的多数请求，被新注册域名、风险类别这些策略给拦下来了。这说明，在恶意域名还没充分进入威胁情报之前，访问策略也有可能掐断一部分攻击路径。当然，结果取决于具体的部署和策略配置，不能外推成整个行业的拦截率。  
  
这次事件还暴露了"只封域名"的局限性。Hudson Rock在BBC和汇丰阿联酋相关的样本里发现，可信脚本内部已经嵌了完整的恶意载荷，就算外部下载失败，它仍可能尝试执行内嵌的那份。所以，阻断攻击者的域名，并不等于把已经送到浏览器里的代码移除了；而且回退代码能不能跑起来，还得看浏览器的执行策略怎么约束。  
  
浏览器侧的防护因此得同时盯住三样东西：脚本内容、动态依赖、外连目的地。只发现"文件变了"还不够，因为A/B测试本身就会合法地更新代码。产品需要帮客户分辨清楚哪些是正常发布、哪些是异常修改，还要能把告警关联到具体的项目、页面和版本上。  
  
内容安全策略CSP可以限制脚本、连接和框架的加载，但效果好不好取决于规则怎么写的。把供应商域名加进允许列表，并不代表就验证了这个域名返回的内容Optimizely当前文档里的示例用了nonce和strict-dynamic；在支持的浏览器中，这种组合能把它对获准脚本的信任，传递给这个脚本动态加载的后续脚本。可问题在于，根脚本一旦被污染，后面加载的东西也可能一路放行。所以策略设计时必须把"可信依赖自己失守"这种情况考虑进去。  
  
子资源完整性校验SRI则是另一条路：用一个事先定好的哈希，检查下载下来的内容符不符合预期。但实验代码正常更新也会改变哈希，这就需要客户的审核与发布流程同步跟上。如果你的流程是自动接受供应商给的每一个新版本，那其实就形不成独立校验了。对动态脚本来说，完整性保护本质上是个发布管理问题，不是加一个属性就能搞定的事。  
  
对企业用户来说，  
应急响应需要从"某某品牌受影响"这种粗粒度，细化到具体页面、具体时间段和具体用户行为。  
  
接了这类服务的企业，应该尽快把受污染的脚本停用或者隔离掉，同时把历史文件和日志保存好。接着去核对受影响的项目、脚本版本、引用页面和交付时段，然后再判断用户有没有在这些页面上进行过支付、复制过收款地址，或者提交过其他敏感信息。  
  
这些关联关系决定了后面该做什么。如果支付字段可能被读取，那就得核查相关交易和支付数据的风险；如果可读取的会话凭据可能外泄，那就应该评估要不要撤销对应会话。光因为品牌出现在名单里，就要求全部用户执行同一套处置动作，既可能把恐慌放大，也可能把真正需要优先处理的风险给盖住。  
  
企业还应该重新评估敏感页面上的第三方功能。登录、账户恢复、支付、管理后台这些页面，每多一个脚本，都该有明确的业务必要性和适用范围。能挪出敏感页面的功能，就考虑挪出去；能限制运行范围、或者用隔离方式实现的，就该评估一下相应的架构怎么调。  
  
对普通访问者来说，这次事件说明了一件事：只逛知名网站，也不能完全排除恶意代码的风险。用户这边能做的，是保持浏览器和操作系统更新，并且在收到明确通知之后，检查一下相关的支付、转账和账户活动。但更关键的责任还是在网站运营方：通知得说清楚具体是哪个域名、哪个时段、可能影响到哪些操作，这样用户才知道该做什么有针对性的处理。  
  
对供应商而言，只要你能向客户页面发布JavaScript，那就得承担起"生产代码发布渠道"这份安全责任。  
  
这类平台的控制台、API、集成接口、后台支持路径，都有可能影响最终交付给客户的代码。最小权限、客户之间的权限隔离、高影响变更的审批、异常修改检测、版本留存和快速回滚，这些都该围绕"能发布代码"这个能力来设计。多因素认证对保护正常登录确实有帮助，但它替代不了对注册、授权和代码发布流程本身的安全验证。  
  
Optimizely已经公开指出了有问题的注册流程，但还需要进一步解释：攻击者为什么能修改多个客户的项目？修复之后又怎么验证相关权限边界确实恢复了？客户需要的是自己能拿去核对的东西——项目记录、被污染的版本、交付时间和清理证据。  
  
恢复服务这件事，也不能只检查当前CDN上的文件。已经打开的页面和缓存副本同样要纳入评估；而且已经完成的数据外传或者资金转移，不会因为上游脚本恢复正常就自动撤销。供应商的通报应该让客户分清楚三件事：哪些代码已经被清除了，哪些访问可能发生在污染期间，以及哪些后果还在调查之中。  
  
对那些还在用第三方实验、营销和分析平台的企业，下一步不妨从三个具体问题开始：  
谁有权改变生产页面，谁批准这些变化，异常代码又怎样被发现和撤回。  
这三个问题应该在接入的时候就有答案，并且在供应商真出事的时候，能够被验证。
