**我们为什么要造自己的 Harenss**  
  
  
  
很多 AI 从业人员或安全服务人员会认为网络安全 Harness 就是"渗透测试 Harness"，这是个非常大的误区。相反渗透测试 Agent 或者说代码审计 Agent 只是网络信息安全的一个小领域。安全从业人员的日常工作显然远不止黑盒渗透：SDLC 的灰盒代码评估、蓝队值班的告警与流量分析、审计未脱敏数据、甲方台账巡检、面向几十万家下级单位的监管评估；要解决的问题甚至还不止这么多.

图四：再造一个 Harness 还有意义吗？  
  
扪心而问，很多渗透测试 Agent 的水平赶不上 WorkBuddy 多跑几轮，也赶不上 Pi 只提供 bash 与文件读写的基础型通用 agent；Claude Code 放开限制（Clawgod）仍有不俗的安全工作能力。随着模型能力提升，如何保证通用 agent 在执行流程上满足安全领域的 Harness 需求？靠架构、知识图谱、Ontology、控制论？基模公司巨头有更高研发成本、更专业的流程和更强内部模型——有什么理由安全公司能在 Harness 架构这种通用问题上超过他们？超过了也会被瞬间抄走，价值的衡量已经不是技术本身，而是有多少人用、烧掉多少 Token、产生多少价值、有多少合同产值。

BugFind 从一次审计任务的固定源码快照开始建立项目上下文。由 Argus SAST 提供确定性结果，Semantic IR v3 提供跨文件关系，SAST-Blind 保持独立探索，Harness Agent Swarm 蜂群再把这些事实交给不同角色的 Agent 逐步调查、交叉质询和验证。我们让 AI Agent 深度参与完整的代码审计过程：理解项目结构、分析代码逻辑、调用安全分析工具、定位潜在风险、追踪数据流和调用链，并结合研发上下文输出可理解、可验证的审计结果。兼顾自动化分析与人工审查。对于明确的规则型问题，可以通过代码扫描快速发现；对于业务逻辑、跨文件调用、复杂数据流、AI Skill 等更依赖上下文理解的问题，则由 Agent 进一步分析。

**BugFind 核心能力**  
  
  
#### 01｜SOTA 级长程自主任务链路能力  
  
BugFind 的任务链路面向仓库级长程审计而设计。在任务开始前Agent 会自主全面了解该项目仓库的语言、框架、入口与权限边界，并据此生成动态任务图，节点类型由基础十类组成：覆盖规划、基线排查、Swarm 蜂群调查、反证查漏、独立挑战、静态验证、动态验证、漏洞回归、归并与报告。该链路支持在后台静默托管，7*24 小时持续运行，自主完成从测绘到报告的长程任务。

图十一：某仓库项目使用 AI 审计 Ultra 模式自主审计 11h 22m、产出111 个风险项  
#### 02｜Ultra 级无上限 Swarm-Agent 集群能力  
  
BugFind 采用自研Agent Swarm 架构算法，由多个 SubAgent 按角色分工协同完成审计任务，角色与数量根据当前仓库的风险面动态确定，并非固定套用模板形式；各 Agent 共享同一套代码图谱与语义事实，并行推进调查、查漏与验证。为降低先看到扫描结果带来的锚定偏差，高危、严重与等级未知的候选以及静态规则来源的候选，会以去重后的复核组为单位各做一次隔离补充复核，复核者不接触候选来源、原始结论与对方意见。BugFind 同时设计 SAST-Blind 盲审独立线，盲审 Agent 的工具列表不包含读取 SAST 结果的能力，服务端对其请求予以拒绝，下发的语义事实会去除 role、evidence 等标签并清空 sanitizer 列表，这样大幅度减少了 LLM 幻觉与死循环的问题产生。

#### 03｜全量代码仓库图谱级取证推理能力  
  
BugFind 以自研 Argus SAST 3.0 引擎作为底座，该引擎离线运行，覆盖 13 个语言与扩展配置、19 个框架语义模型。同时 Semantic IR v3 引擎将函数、变量、调用、控制流与数据流纳入同一张可查询的图，Agent 在审计过程中对参数来源、传递路径与危险调用的判断均基于该图完成，而不是直接依赖LLM对代码片段的直接阅读。由于图由确定性计算生成，相关结论可按当前快照回放，每条结论均落回文件、行号与符号，适用于几万至几十万行规模仓库。

**BugFind 适用场景**  
  
  
  
BugFind 适合存在持续研发、安全审计或代码质量管理需求的组织，而不是只做一次漏洞扫描的场景（  
适用于中大型软件研发企业、互联网和 SaaS 企业、金融、能源、政企等高安全要求行业、网络安全公司和安全服务团队、拥有 DevSecOps 建设需求的企业）  
  
**1、研发过程中的持续代码安全审查：**  
企业每天可能产生大量 Commit 和 Pull Request，传统模式通常依赖研发人员进行 Code Review，安全团队很难逐个参与。BugFind 可以针对代码变更自动执行安全分析，在代码进入主分支前发现潜在风险。研发提交代码 → 创建 PR → BugFind 分析代码变更 → 发现安全问题 → 输出风险说明 → 研发人员确认和修改；持续的改进我们的 DevSecOps 流程。

面对几万、几十万甚至更多行代码时，仅靠人工逐文件审计成本较高。BugFind 可以先通过规则扫描定位高风险区域，再由 Agent 根据代码上下文继续分析，从大量代码中筛选值得人工关注的问题。
