# 【安全速报】11月4日高危漏洞紧急预警  
  
2026年11月04日  |  探知安全  
  
今日焦点  
  
本期六条漏洞横跨 Web 站点、虚拟化集群、语音网关、电商后台、手机终端与 5G 核心网，但真正把它们串成一条线的不是分数，而是**"补丁不是终点，暴露面才是"**  
。头条是刚刚在 11 月 3 日被 CISA 收进 KEV 的 **CVE-2026-119977**  
（Wordfence 给 CVSS 8.1）——WordPress 核心在整包升级时会把新版本解包到一个**路径可预测**  
的临时目录，而那份拷贝里带着安装器，攻击者只要在那几秒里抢到请求就能让未认证访客执行 PHP；补丁 10 月 28 日发出，攻击流量当天就跟着到，Wordfence 24 小时内拦下 62969 次请求。第二条是 **CVE-2026-112816**  
（CVSS 10.0）：Canonical 的 LXD 与 MicroCloud 在校验 mTLS 客户端证书时遍历了整条证书链，只要链上有任意一张受信任的**公开**  
证书就放行，攻击者根本不需要私钥就能冒充管理员直至拿下宿主机 root。第三条 **CVE-2026-116779**  
（CVSS 9.8）已被 FreeSWITCH 厂商明确确认在野利用，而修复版 **v1.11.3 早在 8 月 28 日就发布了**  
，公告却迟了 61 天——这两个月里没升级的存量语音服务器一直在裸奔。第四条 **CVE-2026-118539**  
 是 Drupal Commerce Core 的授权缺失，Drupal 自己评为"高度危急"（21/25）且确认在野利用，约 4.2 万个站点受影响，但它不落地 Web Shell、不装木马，痕迹**只在订单表里**  
。另外两条边角同样扎手：8 字节 WAP Push 短信就能远程崩掉安卓机且 Android 12/13 永远等不到补丁的 **CVE-2026-58882**  
，以及把**根 CA 私钥明文提交进代码仓库**  
的 free5GC **CVE-2026-115925**  
（8.7）。本期六条里有四条的处置动作落在补丁之外——网络隔离、凭据轮换、业务对账、日志回溯，优先排查顺序请看文末处置建议。  
## 漏洞详情  
  
严重  
CVE-2026-119977  
CVSS 8.1  
### WordPress 核心更新窗口竞态，未认证 RCE 被 CISA 收进 KEV（CVSS 8.1·CISA KEV 11-03 新增 / 截止 11-06）  
  
CVE-2026-119977 是 WordPress 核心更新器里的一个时间检查到时间使用（TOCTOU）竞态条件，CWE-362。当站点执行**整包核心升级**  
时，受影响版本会把新版本解包到 wp-content/upgrade  
 下一个**名字完全可预测**  
的临时目录，而这份临时拷贝里包含 WordPress 安装器 wp-admin/setup-config.php  
。由于该目录位于文档根下、且此时旁边没有已存在的 wp-config.php  
 阻断安装器，未认证攻击者只要在解包完成到清理完成之间的那几秒里请求到暂存路径，就能与这份暂存的 WordPress 交互并推进到 PHP 代码执行。漏洞由 Picus Security 的 Umut Bayram 报告，WordPress 官方在 10 月 29 日发布公告 GHSA-4w3m-c66w-69mg  
 将其评为 **Low**  
，而 Wordfence 在自己发布的 CVE 记录里给到 **CVSS 8.1 High**  
（向量 AV:N/AC:H/PR:N/UI:N/S:U/C:H/I:H/A:H  
）——两种评分描述的是同一条未认证代码执行路径，Low 权衡的是单站点那几秒的窗口，High 权衡的是赢得它之后的后果。  
  
时间线值得单独说：WordPress 7.1.4 于 **10 月 28 日**  
发布并向 7.0.8 到 4.7.39 的每一个分支做了回移，10 月 29 日发布公告，**10 月 31 日**  
才由 Wordfence 分配 CVE 编号，而 **11 月 3 日**  
被 CISA 收进 KEV，联邦机构修复截止日 **11 月 6 日**  
。攻击却比 KEV 收录早得多：Wordfence 的防火墙规则在 10 月 28 日 20:30 UTC（发布约三小时后）就下发给付费用户，**9 分钟后出现首次命中**  
，前 21 小时里超过 18500 次请求直指暂存安装器路径，24 小时内累计拦下 **62969 次**  
；两个最大来源对一组小站点持续轮询了约 14.5 小时，其余来源在轮换暂存目录名与版本号变体——这不是在赌某个站点，是在等全网任意一次更新开始。另外一个容易踩的坑：**修复本身不保护携带修复的那一次更新**  
，因为执行解包的还是旧版更新器代码，7.1.4 保护的是下一次升级；更要命的是当自动更新因 PHP 执行上限超时或文件系统权限报错而中断时，那个可预测的暂存目录会**永久留在磁盘上**  
，暴露窗口从几秒变成无限长。  
  
影响范围  
  
WordPress 核心 **4.7 至 7.1.3**  
 全部受影响。修复版本除 7.1.4 外已回移至各分支：4.7.39、4.8.34、4.9.35、5.0.31、5.1.28、5.2.30、5.3.27、5.4.25、5.5.24、5.6.23、5.7.21、5.8.19、5.9.20、6.0.18、6.1.16、6.2.15、6.3.14、6.4.14、6.5.14、6.6.11、6.7.11、6.8.12、6.9.11、7.0.8。  
  
**修复建议：**  
立即升级到 7.1.4 或所在分支的回移版本，**不要跨分支跳跃升级**  
（兼容性风险更大）；升级前把 wp-content/upgrade/  
 从 Web 可达路径里封掉（Nginx 用 location ~* ^/wp-content/upgrade/ { deny all; }  
，Apache 用对应 <Directory>  
 规则），并禁止 PHP 在该目录下执行；Wordfence 用户务必确认防火墙已启用 **Extended Protection 模式**  
（让防火墙在 WordPress 之前拦截直接 PHP 请求），免费版规则的 30 天延迟要到 **11 月 27 日**  
才生效，别把保护窗口压在免费用户身上。  
  
满分  
CVE-2026-112816  
CVSS 10.0  
### Canonical LXD / MicroCloud mTLS 证书链校验倒置，无需私钥冒充管理员（CVSS 10.0·CWE-295 / 未入 KEV）  
  
CVE-2026-112816 是 Canonical 旗下 LXD 容器管理引擎与 MicroCloud 集群平台上一个满分级的认证绕过。LXD 与 MicroCloud 通过 mTLS REST API 暴露管理接口（默认 TCP 8443），客户端接入时需出示证书并在 TLS 握手的 CertificateVerify  
 阶段证明自己持有**叶证书**  
对应的私钥——协议规范只对链首那张叶证书做私钥持有证明，链上其余 CA 或附加证书的私钥**协议层根本不校验**  
。缺陷在于服务端比对信任库时没有把校验限定在叶证书上，而是**遍历了客户端上传的整条证书链**  
：只要链中任意一张证书存在于受信任指纹库中，服务端就判定该连接具备合法管理员身份。攻击者只需拿一张**受信任客户端的公开证书**  
（X.509 公钥证书是明文公开凭据，在集群 join 过程中即可截获），挂在自己控制的叶证书后面发进握手，就能在不持有对方私钥的情况下被当成该客户端登录。Canonical 明确警告：如果被冒充的账户是高权限账号，攻击者可获得**宿主机的 root 权限**  
，进而控制集群内的虚拟机与存储、横向移动到其他节点、建立持久化 C2，最终在整个 MicroCloud 集群内投放勒索。  
  
这个漏洞最早并非 Canonical 自查发现，而是由社区分叉项目 **Incus**  
 报告，Incus 在 7.6.0 修掉了同一问题（该版本同时修了另外 17 个安全缺陷），Canonical 确认 LXD 也受影响后发布了修复版本。值得注意的是暴露面的差异：独立运行的 LXD **默认不开放网络 API**  
，只监听本地 socket，除非管理员显式开启 core.https_address  
；而 MicroCloud 集群的弱点在于 Canonical 明确指出——**能截获某个成员加入集群时的公开证书，就能以该成员身份登录**  
，而集群 join 流量对任何内部人员或已被攻陷的工作负载都是可见的。CVE 记录上带有 CISA 于 10 月 30 日的评估：**未发现被利用**  
，不在 KEV 目录，也没有公开可用的利用代码。截至 10 月 28 日的检查显示，free5GC 那类"明文私钥进仓库"的问题在 free5GC 尚未修（见本期第六条），而 LXD 这边根 CA 私钥并未随源码分发。  
  
影响范围  
  
Canonical **LXD 4.0.14、5.0.10、5.21.8、6.9 及更早版本**  
（即各分支修复版之前）；**MicroCloud 2.1.5 与 3.4.1 之前版本**  
；**Incus 7.6.0 之前版本**  
。Ubuntu 官方仓库中的 LXD 包标记为不受影响或未随附，修复以 **snap**  
 形式发布。仅使用 Docker、Proxmox VE 自带 LXC 容器的用户不受影响。  
  
**修复建议：**  
snap 安装的用户执行 sudo snap refresh lxd  
 与 sudo snap refresh microcloud  
，但**刷新后一定要核对实际版本号**  
——Canonical 在发布公告时这些修复点版本仍在从 candidate 渠道向 stable 滚动推送，别默认刷新完就一定到位；Incus 用户升级到 7.6.0。Canonical 对 LXD **没有提供临时 workaround**  
，Incus 也明确表示除限制监听器网络访问外无配置级修复，因此升级前唯一的动作是**在网络层限制谁能访问 8443 端口**  
，并把集群 join 流量也纳入监控——这一条对 MicroCloud 尤其重要，因为它的利用前提恰恰是"能看见成员加入时的证书"。  
  
严重  
CVE-2026-116779  
CVSS 9.8  
### FreeSWITCH SIP 聊天消息触发任意 API 命令，厂商确认在野利用（CVSS 9.8·修复版早于公告 61 天）  
  
CVE-2026-116779 影响开源电话交换平台 FreeSWITCH。处理入站 SIP MESSAGE 时，FreeSWITCH 把收件人用户名按加号切分后当作"聊天协议名"派发，而名为 api  
 的派发目标会**直接执行任意 FreeSWITCH API 命令**  
。这意味着一条 SIP 聊天消息就能在服务器上执行任意命令，CVSS 9.8。修复版 **v1.11.3 早在 8 月 28 日就发布了**  
，release notes 里只有一行不起眼的 Add enable-chat-api-proto to gate the api chat proto  
——给 api 聊天协议加一道门禁，没有任何通告解释这道门禁防的是什么。厂商 SignalWire 一直到 **10 月 26 日至 28 日**  
才集中发布一批安全通告，其中 GHSA-mg63-h38w-8p9p  
 明确写到该命令执行路径的利用**已在野外被观察到**  
。这 61 天的静默窗口对防御方是双重不利：攻击者有两个月时间从容摸索并武器化，而防守方连"该升到哪个版本"都不知道从何得知。  
  
影响面在语音基础设施这一侧特别值得警惕：默认配置即中招，只要对应 profile 没有显式关闭聊天处理。国内大量呼叫中心、语音机器人、AI 外呼平台基于 FreeSWITCH 自建，这类系统的攻击面往往不在安全设备的视野里，因为它们挂在"业务系统"而非"IT 基础设施"的名下。厂商列出的三项缓解**每一项都只是关门、不是拆通道**  
：enable-chat=false  
 可以整个关掉不需要聊天功能的 profile 的 MESSAGE 处理（最有效，但要求确认业务真的不用 SIP 聊天）；删除目录里所有无密码无哈希的用户，能消掉"无账号即可打"的放大器；disable_system_api_commands=true  
 会移除 system 命令，但**派发路由本身还在**  
，攻击者仍可触达 lua、模块加载、呼叫控制等其余 API。  
  
影响范围  
  
FreeSWITCH **≤ 1.11.2 全部版本**  
，默认配置受影响。修复版本 **v1.11.3**  
（8 月 28 日发布），新版默认拒绝 api 聊天协议并返回 403。  
  
**修复建议：**  
升级到 v1.11.3 是唯一完整解，三项缓解都只是过渡。在野利用已被厂商确认，因此**升级完成后必须按失陷事件处理**  
，而不是打完补丁就收工——核对配置与凭据是否有异常变更、排查可疑的呼叫记录与进程外命令执行痕迹。检测上抓两处：一是 v1.11.3 的告警日志，修复版会对被拒绝的 api 协议请求记录 WARNING 且内容包含来源地址与请求的命令，日里出现这类条目说明已经有人在探；二是存量版本上翻 SIP MESSAGE 的处理记录，**凡是 To 用户名带 api 加号前缀的入站消息都值得逐一核对**  
。  
  
严重  
CVE-2026-118539  
CVSS 6.5  
### Drupal Commerce Core 授权缺失，Drupal 确认在野利用、约 4.2 万站点受影响（CVSS 6.5·Drupal 评"高度危急"21/25）  
  
CVE-2026-118539 是 Drupal Commerce Core 模块的授权缺失问题，CWE-862。Drupal 官方通告 SA-CONTRIB-2026-254  
 的表述是：该模块"未充分保护某些路由与某些实体字段，导致访问绕过，**可能对商家造成财务影响**  
"。漏洞在 10 月 28 日随修复版本一同发布，Drupal 安全团队将其评为 **Highly critical（21/25）**  
 并明确说明**正在被在野利用**  
；加拿大网络安全中心在 10 月 30 日重复了利用警告，BleepingComputer 估计该模块的装机量超过 **4.2 万个站点**  
。CVE 记录上 CISA 数据管道给出的通用评分为 **6.5**  
——这个分数与"高度危急"并存本身就是本期最值得记一笔的地方：**分数反映的是单点严重度，不反映有没有人在敲门**  
。  
  
漏洞的性质决定了它的取证方式与其他所有条目都不同。Commerce Core 是把 Drupal 站点变成商店的模块：购物车、结账表单、headless 前端调用的那些 API 全在这里。授权在 Drupal 里是**逐条路由写的**  
，漏掉的是没有被列进去的那几条——检查表上每一条都通过，表本身不完整。攻击者猜测 URL 即可越权访问受限内容，并可通过 JSON:API 接管其他商户的商品变体与优惠券。关键在于：这是一个**业务逻辑型漏洞，它不需要执行代码**  
，所以被入侵站点那套 PHP 站点的常规信号（新文件、异常进程、对外连接）**可能一个都不会触发**  
。痕迹如果存在，就在订单表里，而那些订单看上去就是一笔普通销售。这直接改变了处置的先后顺序——升级能在几分钟内止住新的滥用，但对**升级之前已经被改动、被少付、被强行走完结账流程的订单毫无作用**  
，那些差异会留在你的账簿和发货队列里，直到有人去对一次账。报告者三人（Puccetti、Johansson、Snyder）均未公开技术细节，攻击起始时间也没有被说明，因此**排查起点要放在 10 月 28 日之前相当宽的一段时间**  
，建议从 9 月初起算。  
  
影响范围  
  
Commerce Core **8.x-2.x 分支 2.41 之前**  
全部版本，以及 **3.0.0 至 3.3.12**  
。修复版本为 **3.3.13**  
 与 **8.x-2.41**  
。注意部分早期报道把受影响范围写成"至 2.41 / 至 3.3.13"，读起来像是修复版本本身也有问题——**不是**  
，Drupal 通告明确 2.41 与 3.3.13 就是关闭该洞的版本。3.x 分支运行在 Drupal 10.3 与 11 上。**升级 Drupal 核心不修此洞**  
，Commerce Core 是独立模块。  
  
**修复建议：**  
立即升级 Commerce Core 至 3.3.13 或 8.x-2.41，通告**未提供可行变通方案**  
，只有升级这一条路，所以必须提前排业务窗口而不是等它变成紧急变更。升级后把**订单对账做成例行动作**  
——金额、状态、折扣、退款四条要有明确的对账口径，且**起点选在 10 月 28 日之前足够远的位置**  
（建议 9 月 1 日起），异常要能在业务侧被发现而不只是安全侧。同时审计商品变体、优惠券与管理员账号，核对是否有被创建或篡改的记录；临时可用 WAF 限制受影响端点并收紧基于角色的权限，但这只是争取升级时间的权宜之计。  
  
严重  
CVE-2026-58882  
CVSS 9.1  
### 安卓"死亡短信"：8 字节 WAP Push 远程崩机，Android 12/13 永远等不到补丁（CVSS 9.1·PoC 已公开 / 旧版本无修复）  
  
CVE-2026-58882 被独立研究者 Mark Blaszczyk 称为"SMS of Death"。整个 payload 只有 **8 个字节**  
：01 06 88 80 80 80 00 BE  
，以数据短信形式发往 WAP Push 端口 2948。根因在 WapPushOverSms.decodeWPdu()  
：头长度按 uintvar 读成 long 后**直接强转 int 且无范围校验**  
，那 5 个字节 88 80 80 80 00  
 按 uintvar 展开是 0x80000000  
，强转成有符号 int 就是 **-2147483648**  
，随后 new byte[headerLength]  
 抛出 NegativeArraySizeException  
，而它发生在 telephony 主线程上且无人接管，com.android.phone  
 进程直接死。谷歌漏洞奖励计划最初判定这不是安全问题，最终还是发布了补丁，AOSP 记录显示修复代码写于 **6 月 15 日**  
，内容是捕获短信解码与分发过程中的运行时异常并删除触发问题的待处理消息。  
  
杀伤力不在"崩一下"，而在它**不放手**  
。消息以数据短信进入 raw 队列，不进收件箱、不弹通知，攻击者号码也不会出现在手机上，属于典型的零点击静默攻击。正在进行的语音通话以 CS_DEATH  
 原因被切断，**包括正在拨打的紧急电话**  
；每次进程重启电话服务有 1 到 2 秒空白。更麻烦的是运营商会自动重发未被确认接收的数据短信，导致崩溃反复触发——研究者称一条消息就造成了长达一周的间歇性断服，连续发送约 **20 条**  
可让设备陷入重启循环，若快速连发约 30 条，崩溃还会与电话服务写入短信存储的 SQLite 进程产生竞态，损坏短信数据库，此后设备每次开机读取损坏存储时 com.android.phone  
 立即崩溃，普通重启无法恢复，恢复出厂设置也只能临时缓解，因为运营商仍在重发。研究者已在 Pixel 9（2026 年 4 月固件）、多款三星 Galaxy 与 A 系列机型上测试，**复现率 100%**  
。  
  
这个漏洞还带出一层监管面的连锁后果：由于攻击可以让手机无法拨打紧急电话，澳大利亚的监管流程要求运营商主动识别无法接通 000 的手机、协助用户换机，并最终对无法呼叫紧急电话的设备停止提供服务，Telstra 明确表示 **28 天内不处理就会封锁该设备**  
——远程攻击制造出的"无法拨打紧急电话"状态，反过来触发监管流程把受害者的手机从运营商网络拉黑。  
  
影响范围  
  
Android **12 至 17**  
 受影响。谷歌已在 **2026 年 10 月的安全更新**  
中为 Android 14 至 17 提供修复（更新说明为 Fix remote DoS in decodeWapPdu  
），但该漏洞**并未出现在谷歌 10 月的公开安全公告清单中**  
；**Android 12 与 13 因已超出安全更新支持范围而不会收到修复**  
，仍在风险之中。PoC 已在 GitHub 公开，演示了如何从一台受控安卓设备向另一台发送攻击短信，可自动化批量实施。  
  
**修复建议：**  
可更新的设备**立刻安装最新安全补丁**  
，安装后按提示重启以完成生效；设备管理侧要**核验补丁级别而不是看型号**  
——制造商与运营商对老机型的推送节奏不一，"已上市旗舰修了"不等于"你手上这台修了"，企业移动终端管理要把 Android 12/13 单独列出来；已进入崩溃循环的设备，恢复可能需要恢复出厂设置或用 ADB 清理待处理短信与损坏的短信数据库，请提前把这段写进 IT 帮助台话术；由于利用在收件箱之前完成，**受害者无法靠查看短信来识别或拦截攻击**  
，不要把排查方向放在"找出那条恶意短信"上；同时评估运营商重投带来的持续触发风险，必要时取出 SIM 卡插入非安卓设备让运营商停止重发（eSIM 设备因无法换卡，对普通用户几乎无法自行恢复）。  
  
严重  
CVE-2026-115926/115925  
CVSS 9.1/8.7  
### free5GC 把根 CA 私钥明文提交进仓库，BSF 管理接口零认证（CVSS 9.1/8.7·PoC 已公开 / 尚无补丁）  
  
free5GC 是开源 5G 核心网项目，实验室、研究机构与私有 5G 项目用它跑 AMF、SMF、PCF 等核心网功能，因此**单个网络功能上的漏洞会波及整个 5G 核心**  
。项目方在 10 月底为两个漏洞发布了含完整技术细节与 PoC 材料的公告，且**截至 10 月 28 日两个漏洞都没有修复版本**  
。  
  
CVE-2026-115926（CVSS 9.1）针对 BSF（Binding Support Function）。BSF 负责跟踪哪个 PCF 为哪个签约用户提供策略服务，但公告指出它的管理 API **完全没有任何认证中间件**  
——而 free5GC 其余每一个网络功能都校验 OAuth2 令牌。这意味着任何能访问到 BSF 端口的人都可以读取、创建、修改、删除签约用户绑定，把某个签约用户的绑定指向一台**伪造的 PCF**  
，SMF 随后就会把策略请求发给这台 rogue 服务器，攻击者由此拿到 QoS、计费与流量门控的控制权；伪造的绑定还会**持久化在数据库中、重启后依然存在**  
。公告直言这条攻击路径能对"整个 5G 核心"发起控制面重定向攻击，并指出 BSF "看起来是在完成认证集成之前就发布了"。CVE-2026-115925（CVSS 8.7）则更直接：项目把**未加密的根 CA 私钥**  
提交进了代码仓库，那把钥匙签发着每一个网络功能的证书，任何拿到它的人都能伪造一张受信任证书冒充核心网服务（仍需中间人位置，因此复杂度略高）。10 月 28 日的检查显示，**仓库里的根密钥仍然存在**  
，BSF 路由也仍然在没有认证检查的情况下注册路由——**这包括 v4.3.0 版本背后的代码**  
。  
  
这条之所以值得单独列出来，是因为它同时踩中两条常被低估的边缘：5G 核心网几乎从不出现在企业的常规 IT 资产台账上，多半被记在"研究/测试环境"名下；而"示例配置里的密钥"这一习惯，恰好把私钥从"部署时才会生成的东西"变成了"任何人都能在网上下载的东西"。截至目前**没有这两条漏洞的在野利用报告**  
，但 PoC 与 Docker 复现环境均已公开。  
  
影响范围  
  
CVE-2026-115926：free5gc/bsf  
 组件 **1754bde 提交之前**  
的版本，随 **free5GC v4.2.3**  
 发行，v4.3.0 背后的代码同样受影响。CVE-2026-115925：**free5GC v1.0.0 至 v4.2.3 及之后版本**  
均含该根密钥。  
  
**修复建议：**  
目前**两份公告都没有列出修复版本**  
，因此不能等升级，要自己动手。第一步是**生成新的根 CA 密钥并重新签发每一个网络功能的证书**  
，任何真实部署都绝不能使用仓库里那把随包附送的密钥——这把钥匙既然公开，就应当视同已泄露。第二步是在网络层**只允许可信的核心网功能访问 BSF 的服务端口**  
；如果业务上根本不需要 BSF 这个可选功能，**直接禁用它**  
是最彻底的处置。同时把"5G 核心网/研究测试环境"这条线单独做一次资产清点，确认到底有哪些 BSF 实例暴露在何处、是否需要这个功能——研究/测试环境严格隔离、禁止公网暴露，是这类项目现阶段唯一能兑现的"缓解"。  
  
紧急提醒  
  
本期最高优先级是 **CVE-2026-119977（WordPress 核心更新窗口未认证 RCE）**  
，理由有三条，且都与"分数"无关：第一，它是本期唯一一条**在 CISA KEV 里、且联邦修复截止日就在 11 月 6 日**  
的条目，也就是说你已经没有观察期了；第二，它的攻击窗口**不在你上线后的稳定期，而在你自己执行升级的那一刻**  
——大量站点开着自动后台更新，全网每时每刻都有人在拆包，都在被扫，很多管理员甚至不知道自己的站点正处于那几秒的暴露之中；第三，最反直觉的一点是，**7.1.4 这个补丁本身不保护"升级到 7.1.4"这一次操作**  
，执行解包的还是旧代码，所以只完成升级然后松口气是错的，必须在变更窗口里保留 Web 层拦截并回看 10 月 28 日之后的日志。如果只做一件事，就把 wp-content/upgrade/  
 从 Web 可达路径里彻底封掉并禁止其下执行 PHP——这一条不依赖你升不升级、也不依赖厂商什么时候公布细节，是当下唯一不依赖任何假设的动作。  
  
其次请注意 **CVE-2026-116779（FreeSWITCH 9.8，厂商确认在野利用）**  
 的特殊节奏：修复版已经发布 61 天，但通告才发出来。这意味着"我们看了公告、按公告升了级"这个动作本身可能是无效的——你很可能升到的是有洞的旧版；而另一方面，厂商既然说了"已在野外被观察到"，**存量系统升完 v1.11.3 之后必须按失陷事件处理**  
，不能打完补丁就收工。语音网关这类系统通常不在安全设备的监控名单里，请优先把它排进排查清单。  
  
最后提醒一条容易被忽略的行动顺序问题：**Drupal Commerce（CVE-2026-118539）这类业务逻辑漏洞的痕迹不在日志里，在业务数据里**  
。升级能止住新的滥用，但对升级前被改动的订单毫无作用——如果你把处置清单写成"升级 Drupal"就结束，那笔钱可能已经少了。**排查优先级建议**  
：WordPress（KEV 截止日最紧，且窗口正在发生）→ FreeSWITCH（确认在野 + 需按失陷处理）→ LXD/MicroCloud（10.0 满分 + 可拿宿主机 root，但未发现被利用）→ Drupal Commerce（在野利用，但损失在账上）→ free5GC（无补丁，靠隔离与换密钥）→ 安卓死亡短信（终端侧，影响面广但可通过补丁缓解）。  
## 处置建议  
  
① **把 wp-content/upgrade/ 从 Web 可达路径彻底封掉并禁止其下执行 PHP**  
，这一步不依赖任何厂商结论，是当下唯一不依赖假设的动作：Nginx 加 location ~* ^/wp-content/upgrade/ { deny all; }  
，Apache 加对应 <Directory>  
 规则并关闭该目录的 PHP 执行；同时**回看 10 月 28 日之后的访问日志**  
，重点找 wp-content/upgrade/  
 与 setup-config.php  
 相关的 GET/POST 请求。  
  
② **立刻确认 WordPress 实际版本并升级**  
，7.1.4 或所在分支的回移版本（4.7.39 / 4.8.34 / 4.9.35 / 5.0.31 / 5.1.28 / 5.2.30 / 5.3.27 / 5.4.25 / 5.5.24 / 5.6.23 / 5.7.21 / 5.8.19 / 5.9.20 / 6.0.18 / 6.1.16 / 6.2.15 / 6.3.14 / 6.4.14 / 6.5.14 / 6.6.11 / 6.7.11 / 6.8.12 / 6.9.11 / 7.0.8）；Wordfence 用户确认已启用 Extended Protection 模式，免费版规则 11 月 27 日才生效，这 20 多天你要自己扛。  
  
③ **升级完 WordPress 不等于干净了**  
：查访问日志里的暂存路径探测、查是否有陌生的管理员账号、查上传目录与 wp-content 下有无异常 PHP 文件、核对核心文件完整性——被拦下的 62969 次请求是扫描，扫描器背后的意图是否已落地，要靠日志和文件说话。  
  
④ **FreeSWITCH 升到 v1.11.3，然后按失陷事件处理**  
：升级前先归档配置文件与凭据基线；升级后核对配置与凭据是否有异常变更、排查可疑呼叫记录与进程外命令执行痕迹；日志侧查 v1.11.3 里被拒绝的 api 协议请求 WARNING 条目（含来源地址与请求命令），存量版本则逐一核对 **To 用户名带 api 加号前缀**  
的入站 SIP MESSAGE；同时清掉配置目录里所有无密码无哈希的用户，并对不需要聊天功能的 profile 关闭 enable-chat  
。  
  
⑤ **LXD / MicroCloud 升级并验证版本，同时收紧 8443 端口**  
：执行 sudo snap refresh lxd  
 与 sudo snap refresh microcloud  
 后**核对实际版本号**  
（修复点版本当时仍在从 candidate 向 stable 推送，别默认到位），Incus 升到 7.6.0；升级完成前用网络策略限制谁能访问 8443，并把**集群 join 流量**  
也纳入监控，因为 MicroCloud 的利用前提正是"能截获成员公开证书"；Canoncial 对 LXD 没有 workaround，这一步不能省。  
  
⑥ **Drupal Commerce 升级后立刻做订单对账**  
：升到 3.3.13 或 8.x-2.41（升 Drupal 核心不修此洞），然后按**金额、状态、折扣、退款**  
四条口径做对账，**起点定在 10 月 28 日之前足够远的位置（建议 9 月 1 日起）**  
，因为官方从未说明攻击从何时开始；同时审计商品变体、优惠券与管理员账号是否有异常创建或篡改。把这条做成例行动作——"把交易类系统的授权复核从按清单核对改成按对象盘点"，凡是没被显式写进授权规则的路径，一律按不可访问处理。  
  
⑦ **free5GC 立即换根 CA 密钥并重签全部网络功能证书**  
，同时在网络层只允许可信核心网功能访问 BSF 服务端口、不需要该功能则直接禁用；同时按"5G 核心网/研究测试环境"这条线单独清点资产（这类系统几乎从不出现在常规 IT 台账上），并严格隔离、禁止公网暴露。  
  
⑧ **移动终端侧核验补丁级别而不是看机型**  
：企业移动管理要把 Android 12/13 单独列出（这两代不会收到修复），确认 10 月安全更新已落到具体设备上；给 IT 帮助台准备好崩溃循环的恢复预案（恢复出厂设置或 ADB 清理待处理短信与损坏的短信数据库），并提醒用户**不要试图靠查看短信来识别攻击**  
——利用发生在消息进入收件箱之前。
