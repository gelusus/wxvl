## 前提  
  
**技术性描述**  
  
① 请求中包含一个资源标识参数（如 id  
），后端对该参数进行了权限校验，直接替换为目标 ID 时返回 403 拒绝访问。  
  
② 同时请求中还包含一组前端互斥的参数对（如 from_city  
/to_city  
、start_time  
/end_time  
），前端逻辑禁止两者取相同值（如出发地与目的地不能相同）。  
  
③ 当攻击者将这对互斥参数设置为相同值时，后端在处理请求时可能因逻辑冲突（如除零、循环引用、断言失败）而进入异常分支，该分支跳过了正常的权限检查，直接返回了目标资源的数据或执行了操作。  
  
**通俗易懂**  
  
① 系统在查某个资源时，会检查你有没有权限看，直接换别人的 ID 会被拦下来。  
  
② 但这个请求里还有一对互相矛盾的参数，比如“出发地”和“目的地”，前端规定它们不能一样。  
  
③ 如果你故意把它们设成一样的值，后端处理时可能出 bug，直接跳过了权限检查，让你看到了别人的数据。  
## 测试流程  
1. 使用低权限用户登录，抓取一个包含资源 ID 和互斥参数对的请求（如查询订单、行程、记录等）。  
  
1. 尝试将请求中的 ID 替换为目标用户/资源的 ID，发送请求，确认返回 403 或其他权限拒绝错误。  
  
1. 保持目标 ID 不变，将互斥参数对的值改为相同的值（如 from=A&to=A  
、start=2024-01-01&end=2024-01-01  
）。  
  
1. 发送修改后的请求，观察响应：  
  
1. 若返回了目标资源的数据（如订单详情、个人信息），则漏洞存在。  
  
1. 若返回 200 且包含敏感信息，进一步验证该数据确实属于其他用户。  
  
1. 可尝试多种互斥参数对（如不同字段名），确认通用性。  
  
## 危害  
1. 攻击者可通过构造矛盾参数绕过权限校验，越权访问其他用户的敏感数据（如订单、个人信息、交易记录），造成隐私泄露。  
  
1. 若接口支持写操作（如修改、删除），攻击者可能利用此漏洞执行未授权的破坏性操作。  
  
## 个人笔记  
  
**IDOR 组合绕过：互斥参数同值化**  
  
请求包存在 ID 参数，直接替换目标 ID 返回 403。同时请求中存在**前端互斥的参数对**  
（如出发地/目的地、开始/结束时间等，前端禁止相同），将其**改为相同值**  
后，后端逻辑校验异常（或跳过权限检查），导致 IDOR 越权成功。
