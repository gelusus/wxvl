# 安全预警｜Java4Shell 高危漏洞披露，附开源检测工具及应急处置指南  
  
2026年11月17日，国外安全研究团队 Calif 公开披露了一个存在于 Java 运行环境中的远程代码执行漏洞，命名为 **Java4Shell（CVE-2026-114938）**  
。  
  
该漏洞存在于 OpenJDK 底层 Base64 解码机制中，在满足特定运行环境及触发条件的情况下，攻击者无需身份认证，即可能造成敏感信息泄露、服务崩溃，甚至远程代码执行。  
  
由于 Java 广泛应用于政务、金融、医疗、能源、工业制造等行业的信息系统，建议相关单位及时开展风险排查和安全加固。  
  
针对本次漏洞，我们已开发并开源本地安全检测工具 **Java4Shell-LocalScanner**  
，帮助企业快速开展风险排查与修复复核。

与常见的 Java Web 框架漏洞不同，Java4Shell 并非源于某个第三方组件，而是存在于 Java 运行环境自身的底层实现中。  
  
即使业务系统采用了最新版本的开发框架，且不存在已知的第三方组件漏洞，也可能因底层 Java 运行环境存在缺陷而受到影响。  
## 02 漏洞影响  
  
漏洞主要涉及 OpenJDK 17.0.6 及之后的受影响未修复版本，包括 Java 17、21、25、27 等版本分支，以及部分特殊版本的 Oracle Java 8。  
  
基于 OpenJDK 构建的多个主流 Java 发行版也可能受到影响，包括：  
- Oracle JDK  
  
- Amazon Corretto  
  
- Eclipse Temurin  
  
- Microsoft Build of OpenJDK  
  
- Azul Zulu  
  
- BellSoft Liberica  
  
- Red Hat OpenJDK  
  
- SAP SapMachine  
  
- Oracle GraalVM  
  
需要特别注意的是，本次漏洞具有一定的硬件依赖性，主要涉及支持 AVX-512 VBMI 指令集的 x86-64 处理器，例如部分较新的 Intel Xeon、AMD EPYC 和 Ryzen 系列处理器。  
  
原生 ARM64 运行环境不受此次特定漏洞影响。  
  
在满足漏洞触发条件的情况下，可能造成以下危害：  
- **敏感信息泄露：**  
 应用内存中的认证凭据、访问令牌、密钥及业务数据可能遭到泄露。  
  
- **业务服务中断：**  
 Java 进程可能因内存破坏发生异常崩溃。  
  
- **远程代码执行：**  
 攻击者可能在 Java 进程权限范围内执行任意代码。  
  
- **进一步安全风险：**  
 受影响服务器可能成为攻击者进一步实施内网渗透和数据窃取的入口。  
  
值得注意的是，并非所有使用 Java 的系统均存在该漏洞的实际利用风险，需要结合 JDK 版本、厂商补丁、CPU 指令集、JVM 配置及业务数据处理场景进行综合判断。  
## 03 开源检测工具发布  
  
**Java4Shell-LocalScanner**  
  
传统漏洞排查通常依赖软件版本识别，但由于 Java4Shell 同时受到硬件架构、CPU 指令集、JVM 运行参数及厂商补丁状态等因素影响，仅通过版本判断容易产生误报和漏报。  
  
针对这一特点，我们开发了 Java4Shell-LocalScanner，一款面向企业安全应急响应的本地只读检测工具。  
### 工具主要功能  
- **Java 环境检测：**  
 识别本地安装的 Java 环境、发行厂商及构建版本。  
  
- **CPU 指令集检测：**  
 判断当前硬件环境是否符合漏洞影响条件。  
  
- **JVM 进程检测：**  
 发现正在运行的 Java 进程，辅助识别实际业务运行环境。  
  
- **缓解措施检测：**  
 检查相关 JVM 安全缓解参数及有效证据。  
  
- **容器环境辅助排查：**  
 支持 Linux 下运行态 HotSpot 库及容器线索核查。  
  
- **批量资产研判：**  
 支持导入 JSON、CSV 格式资产清单，开展离线风险分析。  
  
- **检测报告导出：**  
 支持 TXT、JSON、CSV 格式。  
  
- **跨平台支持：**  
 支持 Windows、Linux、macOS，以及 AMD64、ARM64 架构。

### 二、采取临时缓解措施  
  
对于暂时无法升级的业务系统，可考虑在受影响的 JVM 启动参数中增加：  
  
-XX:-UseBASE64Intrinsics  
  
该参数用于禁用 Base64 硬件加速实现。  
  
也可以在适用的 x86-64 环境中通过以下参数限制 AVX 指令集：  
  
-XX:UseAVX=2  
  
需要注意，第二种方式可能影响其他依赖 AVX-512 的计算性能，且不适用于 ARM64 环境。  
  
调整参数前应进行兼容性测试，并在业务重启后确认缓解措施实际生效。  
  
临时缓解措施不能替代正式安全补丁。  
### 三、开展全面资产排查  
  
建议企业重点关注以下场景：  
- 互联网暴露的 Java 业务系统。  
  
- 统一身份认证、单点登录及 API 网关系统。  
  
- 微服务、Docker 容器及 Kubernetes 集群。  
  
- 内置 Java 运行环境的第三方商业软件。  
  
- 长期未更新的历史业务系统。  
  
- 存在大量外部数据解码处理的应用服务。  
  
完成修复后，应对实际运行进程进行复核，避免出现宿主机 Java 已升级，但业务进程或容器仍在使用旧版本的情况。  
### 四、加强安全监测  
  
建议加强对 Java 应用异常崩溃、异常子进程、异常网络连接、敏感数据访问及身份认证日志的监测，及时识别潜在安全事件。  
## 05 从 PHP2Shell 到 Java4Shell：基础软件安全面临新的挑战  
  
近期，基础软件领域接连披露多起具有较大影响的安全漏洞。  
- **PHP2Shell：**  
 涉及 PHP 底层实现的远程代码执行风险。  
  
- **Node2Shell：**  
 涉及 Node.js Brotli 解压缩功能的安全漏洞。  
  
- **Java4Shell：**  
 涉及 Java 底层 Base64 硬件加速实现的内存安全漏洞。  
  
这些漏洞揭示了一个值得关注的趋势：安全风险不仅存在于业务代码和第三方组件中，同样可能隐藏于编程语言运行时、标准库、底层计算及硬件加速模块中。  
  
随着人工智能技术在代码审计、漏洞挖掘、补丁分析和安全研究中的深入应用，过去需要投入大量人力才能完成的底层软件安全分析，正在逐步提高效率。  
  
一些长期存在于成熟软件中的潜在安全缺陷，也可能被更快地发现。  
  
对于企业而言，未来面临的挑战不仅是漏洞数量增加，更在于从漏洞披露到风险扩散的时间窗口可能进一步缩短。  
  
企业应逐步建立覆盖业务应用、第三方组件、语言运行环境、操作系统及基础设施的全生命周期安全管理机制，提升资产识别、漏洞研判、应急响应和自动化检测能力。  
  
**安全建设不能仅停留在应用层，更需要关注支撑应用运行的底层基础设施。**
