#  Java又爆高危漏洞，OpenJDK远程代码执行漏洞  
原创 网络安全透视镜
                    网络安全透视镜  网络安全透视镜   2026-11-18 03:59  
  
2026 年 11 月 17 日，安全研究机构 Calif Research 公开披露了 OpenJDK 的一处内存破坏漏洞，编号   
CVE-2026-114938  
，代号 Java4Shell。漏洞位于 HotSpot JIT 为 x86-64 平台手写汇编实现的 Base64 解码器 intrinsic 中。攻击者提交一段畸形 Base64 数据，即可触发堆内存越界写入，进而造成堆信息泄露，在部分应用上可实现未经认证的远程代码执行。  
  
同一天，Oracle 与 OpenJDK 分别发布了安全更新。OpenJDK 将该漏洞列为   
hotspot/compiler  
 组件问题，Oracle 在 11 月关键补丁更新中修复了 Java SE 8 至 27 的多条维护线。

01  
  
OVERVIEW  
### 漏洞概述  
  
  
Java 长期以来的卖点之一是内存安全——开发者不必操心指针与越界，JVM 负责内存管理。但这并不意味着 JVM 自身没有内存安全问题。HotSpot 的 JIT 编译器、垃圾回收器、intrinsic 大量使用 C、C++ 和汇编实现，这些底层代码不受 Java 沙箱保护。  
  
Java4Shell 就出现在这里。为了让 Base64 解码跑得更快，HotSpot 把这个函数用   
AVX-512 VBMI  
 指令（VMOVDQU8）重写成 intrinsic，一次能搬移 64 字节数据。这段手写汇编在处理输入末尾的填充字符时，算错了写入掩码。  
  
触发输入简单到有点反直觉：64 个字母 A 加一个等号。  
  
AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=  
  
较旧的 OpenJDK 17 版本因为进入该快路径的长度阈值更高，需要 128 个 A 加一个等号。  
  
Java 层面最终会抛出   
IllegalArgumentException  
 拒绝这个非法输入。但抛出异常时，堆内存已经被写坏了——拒绝得再快也来不及。

Calif 尚未公布完整的 CVSS 4.0 向量字符串，因此两个数字目前无法逐项对齐比较。Oracle 采用 CVSS 3.1 评分，攻击复杂度被评估为 High。  
  
漏洞的危害分为两层。  
  
读——JavaBleed。  
越界写会破坏相邻堆对象的长度字段。攻击者让应用程序把堆内存内容原样吐回响应，这是 Java 版的 Heartbleed。堆里可能包含会话令牌、私钥、个人身份信息，这些都可能随响应泄露出去。  
  
写——远程代码执行。  
通过覆写数组长度字段这一经典手法，固定值越界写可以升级为可控值的线性写，进而触及 HotSpot 的 Code Cache 与 JVM 钩子，实现任意代码执行。  
  
Calif 在默认配置下完成了远程代码执行验证。

漏洞代码与硬件绑定，要求 x86-64 架构且同时支持   
avx512f、avx512bw、avx512vbmi、bmi2  
 四项指令集。ARM64 平台不受影响。  
  
grep -m1 '^flags' /proc/cpuinfo | tr ' ' '\n' | grep -E '^(avx512f|avx512bw|avx512vbmi|bmi2)$'  
  
四个标志必须齐全，缺一个就不受影响。受影响的主流 CPU 包括 Intel Xeon Ice Lake、Sapphire Rapids、Emerald Rapids、Granite Rapids，以及 AMD EPYC、Ryzen 的 Zen 4 及之后架构。  
  
需要注意的是，云主机的实例规格可能被调整，同一台主机今天不受影响，扩容或换机型之后可能就落入受影响范围。  
  
Datadog 在 OpenJDK 17.0.6 上的测试显示，三个解码器入口的行为并不相同。

### 漏洞原理  
  
  
HotSpot 用 intrinsic 实现热点函数，用专用 CPU 指令替代通用编译代码。x86-64 的 Base64 intrinsic 使用 AVX-512 VBMI 指令，一次处理 64 字节。问题出在处理末尾填充的那几行。  
  
这段汇编用   
bzhiq  
 指令构造掩码，作用是保留低 n 位为 1、其余清零。关键缺陷在于：填充处理没有对减法结果做非负校验。  
  
input_mask := bzhiq(-1, input_length) output_len := (input_length / 4) * 3  // 处理填充 if input[input_length - 1] == '=':     output_len -= 1     input_mask >>= 1     if input[input_length - 2] == '=':         output_len -= 1         input_mask >>= 1  output_mask := bzhiq(-1, output_len)  
  
当剩余输入是   
=、==、X=、X==、XY=、===  
 这几种形态时，初始   
output_len  
 已经是 0，处理填充再减 1 或减 2，得到 -1 或 -2。  
  
bzhiq 只从最后一个操作数的低 8 位读取位计数。-1 的低字节是 255，-2 的低字节是 254，两者都超过 64 位操作数宽度，于是掩码保持全 1，也就是   
output_mask == -1u64  
。

— 畸形输入从解码器到 62 字节越界写的完整路径  
  
研究团队用的是 JavaScript 引擎漏洞利用中的经典技术——覆写数组长度字段。把被改写长度的数组称为 writer：长度一旦被撑大，它就会继续接受写入数据。如果在它后面放置另一个对象，就能用可控值破坏那个邻居，固定值越界写因此升级为可控值的线性写。再破坏第二个数组的长度，让它的内容随响应返回，就得到了 reader，也就是前面提到的 JavaBleed 堆泄露原语。  
  
剩下的难点是让这些对象在堆上「恰到好处」地相邻。G1 垃圾回收器把堆划分为固定大小的 region，HotSpot 为每个线程分配私有 TLAB，不同请求线程的分配顺序不可控。团队采用的策略是经典的 Spray and Pray：用对象大小和 padding 把偏移固定在 region 内，喷洒多组 writer/reader 对作为候选邻居，命中失败就重试。  
  
远程利用还要解决分配时机的控制问题。做法是把请求分两段发送：先发到触发关键分配的位置，等 TCP ACK 确保数据已经进入目标机器缓冲区，再发剩余部分。小包分片效果更好。

— 下游发行版修复版本与两个易错点  
  
容器环境需要重建镜像并重新部署。在运行中的容器里直接覆盖 java 二进制文件不是有效的修复方式。  
  
无法立即升级时，可以用 JVM 启动参数关闭缺陷路径。  
  
方案一：禁用 Base64 intrinsic（推荐）  
  
-XX:-UseBASE64Intrinsics  
  
这是范围最窄的方案，只关掉存在漏洞的那段 Base64 向量加速，不影响 JVM 其他 AVX-512 使用场景。在任何架构上都可用。  
  
方案二：限制 AVX 使用级别  
  
-XX:UseAVX=2  
  
整体禁用 AVX-512，会影响其他依赖该指令集的 JVM 操作，需要评估性能影响。这个参数只能在 x86-64 主机上使用，ARM64 的 JVM 不识别它，会直接启动失败。  
  
一个陷阱  
  
-XX:DisableIntrinsic=_base64_decodeBlock 看起来更精准，但没有 -XX:+UnlockDiagnosticVMOption 时 JVM 不会启动。把它放进 JAVA_TOOL_OPTIONS 推给全量节点，等于制造一次批量宕机。  
  
参数生效后需要重启进程，并核验。  
  
jcmdVM.version jcmdVM.flags -all  
  
确认实际进程报告 UseBASE64Intrinsics = false 或 UseAVX = 2。java -version 只报 PATH 上第一个 Java，不代表服务实际在跑的那个。

— 触发条件、处置优先级与排查命令  
  
排查时容易漏掉的地方：容器基础镜像里的 JRE/JDK、第三方商业软件自带的私有 JRE、CI/CD 构建节点、网络设备内置的 Java 运行时，以及 Kubernetes 节点 CPU 规格（Pod 继承节点 CPU，查节点而不是查镜像）。  
  
判断顺序建议：先查 Java 版本，再查 CPU 指令集，再查 JVM 参数，最后查代码里的 decoder 调用和输入可控性。  
  
WAF、网关或应用日志若捕获了 Base64 值，可按以下条件筛选可疑样本：总长度 L（含填充）大于等于 65；L mod 64 等于 1、2 或 3；以一个或两个 = 结尾，且不超过 L mod 64；其余字节属于标准 Base64 字符集。Cisco Talos 已发布对应规则，Snort 2 的 SID 为 1:67502 至 1:67513，Snort 3 增加 1:301754。  
  
JVM 侧监控几个信号：异常崩溃日志（hs_err_pid*.log）、SIGSEGV、堆内存在短时间内异常增长。需要注意的是，捕获 IllegalArgumentException 不会撤销已经发生的越界写；如果写入落在未使用的堆空间，可能暂时看不到任何异常。异常出现的位置与实际内存破坏位置可能相距很远。  
  
仅依赖 WAF 特征串拦截不是长期方案。分块传输、WebSocket 帧、长度非 4 倍数的其他畸形形态都可能绕过这类规则。

DISCOVERY  
### 发现过程  
  
  
漏洞的发现过程本身值得记一笔。研究员 Quang Luong 拉下 OpenJDK HotSpot 源码后，让 OpenAI Codex 像 2026 年的正经安全研究员那样去审计 JIT 编译器、intrinsics、常用 API 和密码学相关代码。  
  
前二十分钟 Codex 给出的结论基本不可用。持续给出更精确的提示后，它报出了 Base64 解码器中的内存破坏问题。发现漏洞约 1 小时，写出第一个可用利用再花 2 小时，全程 token 成本不到 200 美元。  
  
Calif 把这种人机协作模式称为「半人马黑客」——AI 提供算力和广度，人类研究员提供上下文和判断。之后大多数后续利用链几乎由 AI 自主构建。  
  
补丁节奏与利用节奏的对比因此变得尖锐：补丁以周为单位下达的团队，面对一个下午就能出可用利用的对手，窗口不在自己这边。这也是 CISA 同日发布告警、要求优先修补面向互联网系统的原因。
