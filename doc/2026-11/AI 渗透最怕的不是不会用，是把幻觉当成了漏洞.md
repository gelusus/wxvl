AI 渗透最怕的不是不会用，是把幻觉当成了漏洞  
  
Agent 报了个高危，你兴冲冲去复现，敲了三遍——什么都没有。这种事发生两三次，你就不会再信它了。  
  
问题不在模型笨，在你把它的输出当成了结论。AI 渗透真正的门槛，是给它的每条发现建立一条能复核的证据链。  
  
本文讲 AI 辅助渗透的方法与边界，全部示例为教学示意，不指向任何真实目标、不提供针对未修复系统的利用步骤。  
  
01  
为什么 Agent 会「编」出漏洞  
  
先搞清楚一件事：LLM 的本质是补全，不是查询。它会把「看起来像漏洞的代码模式」补全成「一个漏洞」，中间不需要任何真实证据。  
  
这不是 bug，是它的工作原理。你让它找 SQL 注入，它就倾向于给你一段像 SQL 注入的描述——哪怕那个参数根本不存在。  
  
1  
模式匹配式误报：见到字符串拼接就报注入，不管输入是否可控  
  
2  
上下文缺失导致的臆测：只看一个文件，脑补了不存在的调用关系  
  
3  
版本与 CVE 张冠李戴：组件名对得上，版本和影响面全错  
  
02  
一条证据链要有的四样东西  
  
让它交出可验证的物证，而不是一句「这里有问题」。拿不出这四样的，一律按线索处理，不按漏洞处理。  
  
1  
触发点：具体到文件、行号和参数名，能直接定位  
  
2  
数据流：从外部输入到危险操作的完整路径，而不是一句「可能可控」  
  
3  
复现条件：前置状态、认证要求、环境依赖，缺一不可  
  
4  
影响面：能读到什么、能改什么，量化到数据或权限  
  
拿不出这四样的发现，一律按「线索」处理，不按「漏洞」处理。  
  
03  
人工复核的三个动作  
  
拿到 Agent 的输出，别急着复现，先做三步过滤。这三步比任何提示词技巧都管用。  
  
1  
一是核对符号是否真实存在：类名、方法、参数，去源码里搜一遍，搜不到就是幻觉  
  
2  
二是沿数据流自己走一遍，别信它给的路径，尤其别信跨文件的调用  
  
3  
三是把复现条件删掉一个，看结论还成不成立——成立的才是真问题  
  
04  
把复核规则写回提示词  
  
与其每次人工擦屁股，不如把证据链要求固化进 system prompt，让它没证据就不许下结论。  
  
# 证据链要求（教学示意）  
  
对每一条发现，必须同时给出：  
  
  1. 触发点：文件:行号 + 参数名  
  
  2. 数据流：source -> ... -> sink 的完整路径  
  
  3. 复现条件：认证 / 前置状态 / 环境  
  
  4. 影响面：可读取或可修改的具体对象  
  
若任一项无法从给定代码中确认，标记为『待验证线索』，  
  
不得使用『确认存在』『高危』等定性表述。  
  
关键不是让它「更聪明」，是让它「没证据就不许下结论」。把举证责任压回模型这一侧，你的复核成本会降一个量级。  
  
05  
防守视角：误报也是资产  
  
对防守方来说，AI 报出来的误报不是垃圾，是「看起来像漏洞的代码味道」——它往往指向审查盲区。  
  
1  
高频误报点，就是人工 review 该重点看的地方  
  
2  
把复核结论回喂成团队规则，下一次同样的误报就不会再出现  
  
3  
证据链模板本身就是交付标准，人和 AI 用同一套
