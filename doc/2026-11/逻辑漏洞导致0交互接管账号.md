#  逻辑漏洞导致0交互接管账号  
mattwoberts
                    mattwoberts  北山安全   2026-11-27 10:30  
  
Fider 是一款开源的用户反馈收集平台。它的官方安全公告 GHSA-mxx8-x4p9-c9c5（CVE-2026-136165）披露了一个完整的账号接管漏洞：**Fider 仅凭身份提供商（IdP）返回的邮箱地址，就把一次 OAuth 登录关联到已有的本地账号，而且从头到尾不验证这个邮箱到底是不是登录者本人的。**  
  
当系统按 provider 用户 ID 找不到账号时，它会退一步按邮箱查找，命中后就把这次登录的 OAuth 身份绑到那个账号上，并直接签发该账号的会话 Cookie。攻击者只要能让任意一个已启用的 OAuth 提供商返回受害者的邮箱——比如一个  
   
verified_email  
   
为  
   
false  
   
的 Google 账号，或者一个允许用户自选任意邮箱的自建 IdP——就能直接以受害者身份登录。  
  
**管理员和协作者账号还被显式豁免了 provider 角色检查**  
，所以同一手法可以直接接管管理员。原本用来把关 OAuth 注册的账号创建策略，只作用于「新建账号」分支，邀请制、私有租户也拦不住对已有账号的接管。

——代码从头到尾不读

**1. 邮箱被当作可信标识**  
，却没有任何证据证明这名 OAuth 登录者拥有它（oauth.go:135，无已验证邮箱检查）。  
  
**2. 邮箱命中即被视为同一个人**  
，攻击者的 provider ID 被绑定到该账号（handlers/oauth.go:251、300-308）。  
  
**3. 特权账号绕过 provider 角色限制**  
（265-266 行），而邀请制/关闭注册的门槛只在创建新账号时才检查（277 行），关联到已有账号时完全不查。

的 Google 邮箱。但该提交当时没有进入任何正式 tag，最新发布版 0.39.0 仍然受影响。

**前置条件：租户上启用了一个会返回攻击者自选邮箱的 OAuth 提供商**  
  
在内置 Google 登录的场景里，运营方只要开启了 Google 登录即可，攻击者通过自己的 Google 账号提供邮箱。为了做一个自包含、可确定复现的演示，这里用一个自定义 OAuth 提供商走同一条代码路径，其资料接口返回：

**关于真实 provider 的说明：**  
使用 Fider 内置 Google provider 时，前置步骤根本不是攻击者的动作——运营方开启 Google 登录，攻击者用一个  
   
verified_email  
   
为  
   
false  
   
的 Google 账号提供邮箱即可。因为 oauth.go:135 从不读  
   
verified_email  
，从第 1 步起流程完全相同，也不需要管理员做任何配合。上面的自定义 provider 只是用一种确定、自包含的方式，在一次性实例上驱动完全相同的服务端代码。  
  
**影响**  
  
这是一个导致**完全账号接管**  
的认证绕过。任何用户，只要攻击者能通过一个已配置的 OAuth 提供商报出他的邮箱，就能被冒充；又因为管理员和协作者被刻意豁免了 provider 角色检查，同一手法能接管特权账号，把租户的管理控制权（设置、Webhook、用户角色、内容，乃至删除租户）交到攻击者手里。  
  
受影响的是任何启用了至少一个 OAuth 提供商、且邮箱 claim 可被攻击者影响的 Fider 实例——最重要的就是内置 Google 提供商（未验证的  
   
verified_email  
），以及任何允许自助注册或任意邮箱值的自定义 OAuth/OIDC 提供商。受害者账号不需要走邮箱/一次性验证码登录；唯一要求是：目标邮箱对应的账号已经存在。  
  
**修复与缓解**  
  
**修复版本：0.40.0**  
（[#1765]()  
）。现在，Fider 只在 Google 报告邮箱已验证时才采用 Google 登录返回的邮箱，未验证的邮箱不会再被拿来匹配已有账号。  
  
**临时缓解：**  
如果暂时无法升级，在「站点设置 > 认证」中关闭 Google 登录。  
  
**范围说明**  
  
自定义 OAuth 提供商由站点管理员配置，管理员选择信任该身份提供商返回的邮箱 claim。因此只应接入会验证其返回邮箱的自定义提供商。如何调整自定义提供商的处理方式，不在本公告范围内。
