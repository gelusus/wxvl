：Marcus Hutchins 针对「zero-day 没法防」的流行论调给出一条可落地的攻击面收缩方案：给设备管理界面配一个猜不到的子域名，套上 Cloudflare 一类的反向代理，再在防火墙上只放行代理方的 CIDR/ASN——设备从 Shodan、Censys 等测绘索引里整体消失，按 IP 直连也不通，而任何拿到域名的人照常访问，可用性零损失。按他的说法，99.9% 扫描驱动的利用尝试将「根本看不见这台设备」；残余风险只剩愿意花力气挖出子域名的高定向攻击者，而反代的工作方式本身会破坏大量 exploit，WAF 还能再补一层。  
  
这是一条纯防守视角的长推。作者 Marcus Hutchins 在 2017 年注册了 WannaCry 的 kill switch 域名，让那场蠕虫疫情停止扩散，此后长期写面向防守方的科普。本仓库译介过不少攻击者怎么用测绘索引找目标的材料，这条推文正好是硬币的另一面：防守方怎么让自己从索引里消失。全程没有一个高概念，三步全部对着「扫描驱动攻击」的软肋打，照抄就能落地。残余风险和几条推文没展开的边界，放在文末译者补充。  
## 一、场景：每周都在爆 0day 的管理口  
  
Hugging Face 出事之后，安全圈流行起一种论调：zero-day 面前，防守方什么都做不了。Hutchins 觉得这话说得太丧，干脆拿一个最坏的场景做思想实验。  
  
假设你手里有一台企业级网关或防火墙设备——就是那种 Web 管理界面每隔一两周就曝出一个 zero-day 的型号。为了把话说死，他先把两条常规的加固路线也堵上：管理界面下不了线，也配置不成只允许内网访问，它必须对从任何地方连进来的任何人开放。  
## 二、攻击者的软肋：离不开测绘索引  
  
接下来是整条推文的核心观察：绝大多数威胁行为者（包括国家级的）都过度依赖互联网扫描。他们用 Shodan、Censys 这类服务——这些服务扫描每一个 IPv4 地址，把找到的设备全部编成索引。  
  
然后攻击者上场，拿一条搜索语句导出一份「某厂商的某类设备」清单，要么直接批量利用，要么从中挑出感兴趣组织的设备定向下手。  
## 三、三步从索引里消失  
  
方案分三步，不需要采购，也不需要停机。  
  
第一步，建一个不好猜的子域名，比如 firewall-a4f8d5.yourcompany.com。  
  
第二步，注册一个代理/CDN 服务，Cloudflare 或同类均可。配置它把发往这个域名的流量转发到设备的公网 IP，开启反向代理模式。  
  
第三步，回到防火墙加一条规则：管理界面只允许 Cloudflare 的 IP 访问，用 CIDR 或 ASN 白名单都行。  
  
效果立竿见影：这台设备在任何互联网扫描里都不再出现，Shodan、Censys 也扫不到，直接按 IP 访问不通。但任何拿到域名的人照常访问。  
  
用他的原话说，爆炸半径从 “每个 zero-day（不及时打补丁的话还有每个 n-day）都在敲打我这台设备” 降到 “99.9% 的利用尝试压根看不见它”——全程没有牺牲一点可用性。  
## 四、残余风险与适用范围  
  
定向程度高的攻击者可能会多花些力气，挖出你在用的子域名，尝试穿过反向代理来利用设备。但反代的工作方式会破坏很多 exploit，Web Application Firewall（WAF）又加了一层保护。  
  
这类手法对绝大多数 Web 型设备都有效——它们正是被互联网扫描打中最多的一批。对其他软件和设备，也各有大量简单的攻击面收缩办法。在攻击者和目标之间多垫一层，效果往往出乎意料。  
  
最后他把话挑明：「zero-day 挡不住」这种态度，失败主义到家了，也错得离谱。去找你友好的邻居蓝队同学或者威胁情报工程师，讨一份攻击面收缩建议。  
## 译者补充：几点解读与延伸  
  
**设备为什么会「从索引里消失」——机制核对**  
  
原理可以拆开看一眼：测绘引擎认的是 IP 和端口，扫描器必须从自己的 IP 段发起连接才能完成识别。白名单只放行 CDN 一方之后，从 Shodan、Censys 的视角看，这台设备的端口连不上、没有 banner 可取——设备不是被藏得更深，而是压根不在索引里。合法访问走的是「域名 → CDN 边缘 → 回源白名单」这条通道，所以可用性不受影响。  
  
**推文没展开的几条边界**  
- 子域名的保密性没有想象中稳。证书透明度（CT）日志公开可查，给子域名签发过证书就会留痕，被动 DNS 与历史解析记录同样可能泄露。真正拦住攻击者的是 IP 白名单，子域名只负责「不被顺藤摸瓜」，两道防线别混为一谈。  
  
- 白名单本身要维护。CDN 的回源 IP 段会更新（Cloudflare 在 https://www.cloudflare.com/ips/ 公布），列表跟不上时的第一受害者是自己的运维——人被锁在门外。先灰度、留一条带外管理通道，再全量收紧。  
  
- 「从索引里消失」洗不掉历史。设备如果此前被扫过，条目仍在测绘平台的历史数据里，对着时间轴做 diff，甚至能看出某个 IP 从开放转成了过滤。  
  
- 严格说，按 ASN/CIDR 放行的是整个 CDN 平台。以 Cloudflare 为例，其计算产品 Workers 的出口流量同样来自 Cloudflare 的地址空间，把扫描器架在 CDN 平台内部跑的攻击者，未必会被 IP 白名单挡住。把白名单收紧到实际回源段，并在源站启用 Authenticated Origin Pulls 这类 mTLS 验证，比单纯按 IP 放行更稳。  
  
**「99.9%」是修辞，不是测量**  
  
单条推文体量所限，这个数字是个形容，不是实测，全文没有给任何前后对比数据。但这不减损方案本身的价值：它改变的是「被看见的概率」，不是「被攻陷后的损失规模」，在攻击面收缩的措施里属于性价比很高的一档——零采购、零停机、随时可回退。  
  
**与本仓库既有文章的对照**  
  
三篇旧文正好和这条推文凑成一组。Censys ARC 的《播放你的视频：假 MP4 文件里的 NetSupport 载荷》演示攻击者侧的用法：用 body 关键词在 Censys 里批量 pivot 出目标集群，投递基础设施还混用 Cloudflare 前置与裸 IP 源站。测绘索引和 CDN 隐匿是攻防两边共用的同一门手艺，这条推文把镜头转回了防守席。  
  
现实注脚也有两个。GTIG 复盘的 ARMORY CASTLE 行动，打的就是 vCenter Web 管理面的两个零日——推文假设的「隔一两周爆一个的管理口」并不夸张，vSphere 管理面正是现实里被打穿的那类目标。《56 次 AWS API 调用挤在 141 毫秒里》补了另一条入口：不需要 zero-day，失窃凭据一样横扫云管理面；而那篇事后靠 FOFA 自签证书指纹串联出三台同网段 C2，又说明测绘索引同样服务防守方的取证。索引在两边手里各有用途：攻击者拿它找目标，研究者拿它做归因，这条推文补上的是防守方的用法——让自己不出现在里面。
